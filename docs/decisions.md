# Decisions

Newest last. Each entry says what was decided and why, so later changes can weigh the same reasons.

## 2026-10-06: Build a new tool rather than fork granted

granted is AWS-shaped throughout (`~/.aws/config` profiles, STS, console federation), and a fork would mean keeping up with upstream AWS fixes to keep unrelated features working. A new tool borrows the ideas without the coupling.

## 2026-10-06: Name omnifob, command `fob`

"omni" says every cloud; a fob is the small thing that opens your doors. Alternatives rejected: omnicloud (taken by a 656-star project and the GitHub user), omnikey (HID Global's card reader brand), omnipass (Softex's old fingerprint product), omnifox (reads as a fnox fork). Both binaries are installed; `fob` for daily use, `omnifob` for scripts.

## 2026-10-06: Rust

Same language as mise and fnox, which makes a later merge into fnox realistic. Official AWS SDK for Rust, `keyring-core` for every OS keychain, single static binary.

## 2026-10-06: Integrations produce profiles (Leapp's model)

An integration is something you sign in to once; sync discovers its profiles. Users configure a handful of integrations, never hundreds of profiles. Profiles are cached on disk without secrets and refreshed by `fob sync`.

## 2026-10-06: Two crates

`omnifob-core` holds config, storage and providers; `omnifob` holds the command line. Provider code can then move into another project (fnox) without the CLI.

## 2026-10-06: Secrets in the OS keychain through keyring-core

`keyring` v4 itself says applications should link `keyring-core` and pick stores. macOS Keychain, Windows Credential Manager, Secret Service on Linux, falling back to kernel keyutils when no Secret Service is running (WSL, servers). keyutils loses secrets on reboot; acceptable for now. Revisit an encrypted-file store (wrangler has one, `db-keystore` exists) if that annoys.

## 2026-10-06: AWS device flow first

Works on every machine including headless and WSL; PKCE needs a local callback server. aws-vault and granted both default to device flow. Superseded on 2026-11-08, below.

## 2026-10-06: Cloudflare bootstrap token first, OAuth second

Cloudflare's third-party OAuth only allows PKCE (no device flow) and it is unverified whether `account_api_tokens:create` is available to third-party clients. The bootstrap token works today and is a one-click, one-time setup. OAuth comes next, keeping the bootstrap token as fallback. Superseded on 2026-10-09, below.

## 2026-10-06: Permissions by name, not ID

Scoping tokens in the dashboard is the pain omnifob removes, and fnox needs IDs too. Names are resolved at mint time from the permission groups API, so they never go stale in config, and typos get suggestions.

## 2026-10-06: Clean up expired minted tokens

Cloudflare keeps expired tokens listed. Minted tokens carry the `omnifob:` prefix, and after each mint expired ones with that prefix are deleted. Tokens omnifob did not create are never touched.

## 2026-10-06: Shell switching through a wrapper function

A process cannot change its parent's environment, so `fob activate <shell>` prints a `fob` function where `use` and `unuse` eval `fob env`. `fob env` remembers the variables it set in `OMNIFOB_VARS` and removes stale ones when switching. The picker draws on stderr so it works inside `$(...)`.

## 2026-10-06: Credential output formats for other tools

`--format json` (generic), `fnox` (command lease contract), `credential-process` (AWS SDKs). This makes omnifob useful before every provider is native, and is the integration point with fnox.

## 2026-10-07: Release notes in releases only

There is no CHANGELOG.md alongside the release notes. Notes are written once, in the signed tag's message (`--cleanup=verbatim` keeps Markdown headings), and the release workflow copies them into the GitHub release. Generated notes are only a fallback: they list merged pull requests, and changes here have gone straight to main.

## 2026-10-07: Pull requests for changes

Changes go through a pull request, squash-merged after CI passes, matching the repository's merge settings (squash only, title and description from the PR). Small changes (a typo, a log line) may still go straight to `main`. Repository settings match `garysassano/shin-bucket-deployment`, except that Dependabot alerts stay enabled here: the baseline never turns a security feature off to match the reference.

## 2026-10-07: No profile aliases for now

Profile ids are long (`<integration>/<account>/<role or template>`), but they are rarely typed: any words that match one profile select it, a whole-segment match wins, and shell completion fills in the rest. Aliases would add a second naming scheme to learn and keep in sync for little gain. The repeated case, the same profile in the same project, is better served by a per-directory default profile, which is planned. Revisit if real collisions keep forcing long queries; an alias would then be an exact match checked before word matching, so it never changes what existing queries select.

## 2026-10-09: Cloudflare browser sign-in as its own type

Third-party OAuth clients can request "Account API Tokens Write" now (a sensitive scope the consent page leaves off by default), and an access token with it creates and deletes account-owned tokens in every account approved on the consent page. So a browser sign-in replaces the bootstrap token without losing what minting gives: narrow tokens per template, IP limits, R2 bucket limits and S3 credentials, and `--revoke`.

The sign-in method is the integration type, as with `aws-sso`: `cloudflare-oauth` and `cloudflare-token` (the bootstrap token, formerly `cloudflare`). Both share configuration, templates and minting, so a template gives the same token either way. A clean break from `cloudflare` while omnifob is 0.x, named in the release notes.

A sign-in can only mint permissions whose scope the consent granted; Cloudflare refuses the rest. omnifob therefore requests the scopes its templates need, from a table of permission name to scope ID, since the IDs do not follow the names (`page.write` for Pages, `query-cache.write` for Hyperdrive). The OAuth client must have those scopes registered. Until omnifob ships a public client, each user registers a private one; a public client needs a verified domain for its client URL, and making a client public cannot be undone.

## 2026-10-09: GitHub accounts stay with git and Git Credential Manager

omnifob briefly gained per-directory profiles, a git credential helper and a GitHub sign-in, meant to replace a hand-written gh wrapper that picks a GitHub account per directory. All three were reverted before any release.

git's `includeIf` already maps each directory to an account (`credential.https://github.com.username`, next to `user.name` and `user.email`), and Git Credential Manager already keeps one token per account and picks it by that username. omnifob's versions repeated the mapping in a second place, chose by directory while ignoring the username git sends, and needed an OAuth app registered and a sign-in per account. The wrapper could not go away either, since a shell function is invisible to non-interactive shells such as coding agents. The only gain was the `read:org` scope Git Credential Manager does not request, which a classic token stored in it also provides. omnifob keeps the `github` token preset for handing a token to a command; [providers/github.md](providers/github.md) has what was learned.

Per-directory profiles went too: nothing used them yet, and wrangler and `cf` bind accounts to directories themselves. Revisit them when a provider without that needs it, keeping the mapping in omnifob's config rather than in repositories.

## 2026-11-08: AWS browser sign-in by default, device flow as fallback

The AWS CLI has signed in with the authorization code flow and PKCE by default since 2.22.0; the device flow is behind `--use-device-code`. The device flow lets anyone who tricks a user into entering a code take over the session (device code phishing), while PKCE binds the sign-in to a listener on the machine that started it. The 2026-10-06 reason for the device flow no longer holds: omnifob has had a loopback callback since the Cloudflare browser sign-in, and on WSL the Windows browser reaches `127.0.0.1` in WSL (checked 2026-11-08). `fob login` uses the device flow with `--device-code`, and on its own over SSH and in containers, where a browser cannot reach the loopback listener (granted makes the same check).

Two details follow the AWS CLI rather than plain OAuth: the client is registered with the portless redirect `http://127.0.0.1/oauth/callback` and the sign-in uses any free port (RFC 8252, section 7.3), and the consent page takes the scopes as `scopes`, not `scope`.

## 2026-11-08: Renew AWS sessions under a lock shared by every process

Each refresh returns a new refresh token, and omnifob treats the old one as spent (as aws-vault does; whether Identity Center refuses a reused one is not verified), so two `fob` processes renewing the same session at once (parallel `credential_process` calls after a laptop wakes, or two background renewals) left the loser with a spent token and a false "session ended". Renewal now runs under a file lock per integration and reads the token again once it holds the lock. A 401 from the portal renews once and retries, and drops the session only if it still holds the refused token, so a session another process just renewed is never thrown away.

## 2026-11-08: IAM users through STS sessions, like aws-vault

granted and aws-vault both support IAM users, and some accounts still have them. omnifob stores the access key in the keychain and never exports it: profiles get a `GetSessionToken` session, and roles are assumed with that session rather than with the key. Roles then get sessions of up to 12 hours (role chaining would cap them at one), and one MFA code covers every role for the session's length. Long-lived keys stay discouraged; this keeps them off disk and out of environments where they exist anyway.

## 2026-11-08: MFA codes through a prompt the embedder registers

`omnifob-core` stays usable as a library, so it never reads the terminal. The command line registers a prompt when stdin and stderr are terminals; elsewhere (background renewal, `credential_process` without a terminal) a profile that needs a code fails with a message saying to run `fob creds` in a terminal first. Fetches are serialized per profile, so parallel `credential_process` calls ask once and share the result.

## 2026-11-08: Google and Azure sign in with their CLIs' own clients

A sign-in needs an OAuth client. Google publishes none for third-party tools, and registering one means a Google Cloud project, a consent screen and, for the `cloud-platform` scope, either verification or a warning page. omnifob signs in with gcloud's installed-app client, as gcloud itself does, so it works wherever gcloud works and needs no setup; `client_id` and `client_secret` name a client of your own instead. Rolle reads the refresh token gcloud leaves in a plain file instead; omnifob keeps its own sign-in in the keychain and does not need gcloud installed. For Azure, the Azure CLI's public client is the default of Microsoft's own Azure Identity libraries for interactive sign-in, so using it follows Microsoft's practice.

Both follow their CLI's flows: PKCE with a `localhost` redirect by default; from another device, gcloud's pasted-code page and Entra ID's device flow.

## 2026-11-08: Modal as a stored token

The Modal CLI creates tokens through its gRPC API (`TokenFlowCreate` and `TokenFlowWait`), which can make them expire, and stores them in plain text in `~/.modal.toml`. Implementing that flow would mean hand-encoding protobuf for an internal API. The `modal` preset stores the token ID and secret in the keychain and hands them out as `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET`, which the Modal client reads before its config file (checked with Modal 1.6.3).

## 2026-11-08: Presets carry fixed variables; Unikraft Cloud as a stored token

Unikraft Cloud has two CLIs. `kraft` (KraftKit) builds unikernels and has a `kraft cloud` subcommand, deprecated with support ending 2026-11-26; `unikraft` (`unikraft-cloud/cli`) replaces it. Both sign in to the same control plane, and the token they keep is a static robot-account credential (`base64(robot$<name>.users.kraftcloud:<secret>)`) with no expiry and no API to mint narrower ones, so the `unikraft` preset stores it. `kraft` reads `UKC_TOKEN` and `UKC_METRO` whenever they are set; `unikraft` reads them only with `UNIKRAFT_PROFILE_ENV=true`, so presets gained fixed variables (`vars`, overridden by the integration's own) and this one sets that flag. Checked live with `unikraft quotas` and `kraft cloud quota`, each given only what `fob exec` exports.

## 2026-11-15: CI runs the OS matrix on the top of a stack, checks the minimum Rust, and runs cargo deny

The Linux, macOS and Windows jobs (`check`, and `msrv` below) run on every push to `main` and on every pull request that is not part of a stack. In a stack of pull requests they run only on the top PR: its tree contains every layer below it, so a pass there covers the whole stack, and running the matrix on each layer would repeat the same builds once per layer on every rebase. The stack is merged once the top PR passes, and the push to `main` runs the matrix again on what was merged. A job-level `if` is enough because `main` has no required status checks, so a skipped job blocks nothing.

`rust-version` in the workspace `Cargo.toml` is a promise, so `msrv` installs exactly that toolchain, read from the manifest, and runs `cargo check --all-targets` on all three systems, since much of the code is behind platform `cfg`s. It runs no clippy or tests, because lints differ between compiler versions. The AWS SDK crates currently set the floor at 1.94.1.

`cargo deny` (`deny.toml`) checks every target and all features, and runs ungated because it takes seconds. Every RustSec advisory and every yanked version fails it. Licences are an allow-list of those in the tree that are compatible with shipping MIT binaries, so a new licence needs a review before it is added. Only crates.io is allowed as a source, and wildcard versions are refused. Duplicate versions only warn, since they come and go with the ecosystem. Three advisories are accepted by ID: RUSTSEC-2026-0370, -0371 and -0372 mark `zvariant`, `zbus_names` and `zvariant_derive` unmaintained because zbus 6 absorbed them, and they reach omnifob only through the Linux Secret Service keyring store (`zbus-secret-service-keyring-store` → `secret-service` → zbus 5). They are notices, not vulnerabilities, and no stable release of that chain uses zbus 6 yet (`secret-service` 6 was a release candidate on 2026-11-15). Drop the three entries once the keyring store moves to zbus 6.

Dependabot opens one grouped pull request a week for crates and one for GitHub Actions, so pins and dependencies stay current between manual update passes.

## 2026-11-15: AWS partitions in one type, read from role ARNs

The console sign-in guessed the partition from a Region prefix, treated every unknown prefix as commercial, and assumed each partition has an unprefixed sign-in host. The European Sovereign Cloud has none, so a portal there without `default_region` sent the sign-in to `signin.amazonaws-eusc.eu`, which does not resolve. `Partition` (`providers/aws_partition.rs`) now holds the partitions with a public console, their ARN names and hosts, and is parsed from the role ARN where a profile has one, since an ARN states its partition and a Region only implies it. The isolated partitions are recognised by their Region prefixes (`us-iso-`, `us-isob-`, `eu-isoe-`, `us-isof-`) and ARN names and refused by name. Without an exported Region the other partitions keep their unprefixed sign-in host, which matches the unprefixed console the sign-in lands on; only the European Sovereign Cloud falls back to the portal's Region. Cross-partition profiles use the same type to check that a source Region and a destination role are in different partitions.

## 2026-11-15: Only a final refresh error ends an AWS session

Every failed refresh used to count as the end of the session: after a 401 from the portal the session was deleted, and an expired token gave "run `fob login`", even when the refresh had only timed out or met a 500. A laptop waking offline, or a brief Identity Center outage, then sent the user through a browser sign-in although the session at Identity Center was intact. `CreateToken` documents which errors are final (`InvalidGrantException`, `ExpiredTokenException`, `InvalidClientException`, `UnauthorizedClientException`, `AccessDeniedException`); only those delete the session and ask for a sign-in. Any other failure keeps the session and reports the cause, with a hint to sign in again if it persists, as the AWS CLI keeps its token cache when a refresh fails. `InvalidClientException` and `UnauthorizedClientException` also delete the refused client's registration, since the next sign-in would otherwise reuse it.

## 2026-11-15: Only this sign-in's callback ends the wait on the loopback listener

The listener behind the four browser sign-ins (AWS, Google, Azure, Cloudflare) served one connection at a time and treated every failure as the end of the sign-in: a connection that sent nothing for ten seconds, as browsers open speculatively, aborted it, and held up the real callback meanwhile; and a callback with another `state`, which any local page or an old tab can send, cancelled it. The listener now serves connections side by side, closes one that has not sent its request within two seconds (and the oldest when more than 64 wait, or when file descriptors run out), answers other paths with 404 and a callback with another `state` with 400, and keeps waiting until the sign-in's deadline. Only a callback with this sign-in's `state` ends the wait, with its code or the provider's `error`; `state` is checked before `error`, since RFC 6749 returns it with errors too, so a refusal without it cannot cancel the sign-in either.

## 2026-11-15: One HTTP client with timeouts for calls outside the AWS SDK

The Cloudflare API client, the stored-token check and the AWS console sign-in built a bare `reqwest::Client`, which has no timeout, so a server that accepted the connection and never answered hung the command. The Google, Azure and Cloudflare OAuth clients each built their own with a user agent but no timeout either. They all now come from `http::client()` in `omnifob-core`: a 10 second connect timeout (the AWS SDK clients use 3.1 seconds), a 30 second limit on the whole request, long enough for the slowest call a provider makes (a token mint or an account listing page), and the `omnifob/<version>` user agent, which Cloudflare's bot protection requires. The Cloudflare trace lookup keeps its own 5 second limit on the same builder.

## 2026-11-15: `fob console` signs in with new credentials

Without `SessionDuration`, a console session lasts as long as the credentials given to the federation endpoint, and `fob console` passed cached ones, which are handed out until five minutes before they expire, so the console could sign the user out almost at once. It now gets new credentials for every console sign-in, for every AWS profile type: `GetRoleCredentials` for an Identity Center role, `AssumeRole` for a chained role and an IAM user's role, and (as before) a new `GetFederationToken` session for an IAM user's own console. The new credentials also replace the cached ones, so the next command reuses them.

The alternative was to keep cached credentials that still had at least half their lifetime left. That saves one call, but the console session would still end at an unpredictable time, as early as half an hour into a one-hour role, and the user cannot tell which they got. A new set costs one fast API call with no prompt for Identity Center roles and IAM users' roles (their user session, and its MFA, is reused). The cost lands on chained roles with `mfa_serial`, which ask for a code each time the console opens, the same as `--no-cache` does; an IAM user's role is also still capped by what is left of the user's session. Chained roles cannot take a console session length, since AWS refuses `SessionDuration` for role chaining. For an IAM user's role, `console_duration` (below) sends one, which AWS documents as independent of the credentials' duration; whether it holds past the end of the user's `GetSessionToken` session is not stated and has not been tried live.

## 2026-11-15: `console_duration` has no default

The federation endpoint's `SessionDuration` (15 minutes to 12 hours) lets a console session outlast its credentials, for credentials from `AssumeRole*` and Identity Center; it fails for role chaining and `GetFederationToken`. `fob console --duration` and a `console_duration` key on `aws-sso` integrations and `aws-iam` roles send it. It is opt-in with no default: `SessionDuration` must be shorter than the role's maximum session duration (for an Identity Center role, the permission set's session duration, one hour by default), omnifob cannot see that maximum, and a value at or above it makes the sign-in fail, so any built-in default would break `fob console` for roles with a short maximum. Left unset, the console lasts as long as the new credentials it is opened with. `--duration` is refused before any call for chained roles and an IAM user's own session, and the integration's `console_duration` is not sent for its chained roles.

The credentials now go to `getSigninToken` in a form POST, which the federation endpoint accepts, instead of the query string of a GET, so they stay out of proxy and access logs and out of error messages, which quote the request URL. `--service` and `--region` build the destination as granted does (`https://<console host>/<service>/home?region=<region>`); the service is the console path as given, without granted's shortcut table, which would need upkeep as consoles move, and the Region is checked against the profile's partition. `Partition` refuses any Region not shaped like one (lowercase words joined by hyphens, ending in a number), in `of_region` and wherever a Region becomes part of a host name: it treats unknown prefixes as commercial so new Regions keep working, and without the shape check a Region such as `attacker.example#` turned the sign-in host into another one, which would have received the credentials.

## 2026-11-15: The credential cache holds the configured lifetime only

A `--ttl` request used to replace a profile's cached credentials, so `fob exec --ttl 15m` once left every plain command after it with credentials of 15 minutes, renewed early and handed out until five minutes before they ended. Credentials asked for with `--ttl` are now not cached, and an IAM user's session started with `--ttl` is not kept as the session its roles are assumed with. The cache therefore holds only credentials of the configured lifetime: those a plain command gets, and the new ones `fob console` gets, which replace the cached ones. A `--ttl` command always asks the provider anyway, so not caching its credentials costs nothing.

`fob sync` replaced an integration's profiles without touching the credentials cached for the ones that went away (an assignment removed, a role taken out of the config, an integration deleted), so keychain entries accumulated. It now deletes `credentials/<profile id>` for every profile the sync dropped or whose target changed under the same id (a chained or IAM user's role whose `role_arn` moved to another account), after the new profile list is saved; such credentials belong to the old target and would otherwise be handed out with the new account's `AWS_ACCOUNT_ID`. A small leak remains: a background renewal, or a command started with the old profile list, can write `credentials/<id>` for a dropped profile after the sync has pruned it, and later syncs no longer know that profile, so the entry stays until it is deleted by hand or the keychain forgets it (the kernel keyring on reboot). Closing it would mean listing the keychain's `credentials/` entries, which not every store can do.

AWS credentials now carry `AWS_ACCOUNT_ID`, and the `credential-process` output `AccountId`, for the SDKs' account-based endpoints. It is added when credentials are handed out rather than by each provider, so credentials cached before the change carry it too. The account is the profile's for Identity Center roles and an IAM user's session (whose account now comes from `GetCallerIdentity`'s `Account` rather than the fourth field of the ARN), and the role ARN's for chained roles and an IAM user's roles, as the profile recorded it at discovery rather than as the config states it now: credentials cached before a `role_arn` edit belong to the old account until `fob sync` drops them, and are labelled with it meanwhile. Only a role profile synced before the account was recorded falls back to the config.

## 2026-11-15: Integration names are letters, digits, `.`, `_` and `-`

Integration names could contain anything but `/`, and a name with a space broke the `credential_process = fob creds <id> ...` line that `fob export aws-config` writes, since the AWS guide requires double quotes around a parameter with a space. `Config::parse` now accepts only `[A-Za-z0-9._-]`, not starting with `-` (the command line would read such a name as an option), rather than the export quoting the id: one rule then covers every place the name ends up, the AWS config line, keychain keys (`aws-sso/<integration>/token`), lock file names (where `a b` and `a_b` would share `aws-sso-a_b.lock`) and the WSL vault's file names, where quoting would have fixed only the first. Account and role labels already went through `slug`, and names `fob import aws` suggests always did. A config with another name fails with an error that names `fob rename "<old>" <new-name>`, which reads the config without the check so it can fix it, and refuses a new name that breaks the rule; `fob cf add-template` refuses such a template name, since template names become the last segment of profile ids. This breaks configs with other characters in a name, which 0.x allows; the release notes name it.

## 2026-11-15: `fob import aws` reads the AWS config as the SDKs do

The AWS CLI v2 keeps an inline comment in a value (`region = eu-west-1 # home` reads as `eu-west-1 # home`, which it then refuses as a Region), while the SDKs' profile parser drops a `#` or `;` comment that follows whitespace. The import follows the SDKs, since a line like that is meant as a comment and the SDKs are what most tools reading the file use. Static keys are not imported at all: profiles that roles are assumed from become `aws-iam` integrations, their key values are dropped while parsing, and the user stores the key with `fob login`, which checks it with STS before keeping it.

## 2026-11-15: Cross-partition roles get their own `cross_partition` table

Roles in another partition, reached with STS `GetWebIdentityToken` and `AssumeRoleWithWebIdentity`, are configured under `[integrations.<name>.cross_partition.<label>]` on `aws-sso` integrations, not as a flag on `chained`. The required keys differ (`audience` and the destination `region`, which a chained role does not need), the duration limits differ (up to 12 hours rather than the one hour of role chaining), and the errors point at different administrators (outbound identity federation in the source account, an OIDC provider and trust policy in the destination). The table is named `cross_partition` because that is AWS's own term for the feature, so it is what a user searches for; `federated` already means three other things in this codebase (console federation, `GetFederationToken`, SAML). The config is checked when it loads, so mistakes surface before any call: `role_arn` must be an IAM role ARN in a partition other than the source Region's, which must be the portal's partition, where the Identity Center role's credentials work; `region` must be in the partition of `role_arn`; `audience` is 1 to 255 characters, since it must equal a client ID of the destination's IAM OIDC provider and IAM takes client IDs up to 255 (`GetWebIdentityToken` alone would take 1000), and `duration` is 15 minutes to 12 hours. A label that would give a cross-partition role the same profile id as a chained role is refused, and one that collides with an Identity Center role at `fob sync` gets a `-cross-partition` suffix and a warning rather than failing the sync, so a renamed AWS account cannot stop `fob sync` from working. The suffix has a risk, which chained roles have shared all along with their `-chained` suffix: if an Identity Center account is later added or renamed so that its slug matches a label, the next sync gives the unsuffixed id to the Identity Center role, and an existing id (in `~/.aws/config`, scripts, shell history) then points at a different role in a different account, with only a warning to say so. Choosing labels that cannot match an account name (such as `gov-audit` rather than `audit`) avoids it. The other direction is checked too: a chained role's `role_arn` must be an IAM role ARN in the portal's partition, since `AssumeRole` cannot cross partitions, so one in another partition is refused at load with a pointer to `cross_partition` instead of failing at the first STS call, and `fob import aws` skips such a profile with that reason. A portal in an isolated partition, which `Partition` does not model, gets the ARN shape check only.

Every Region key on AWS integrations is now checked to be shaped like a Region when the config loads, so a malformed one fails with the key's name rather than at the first command that builds a host name from it. The check is the shape only, not `Partition::of_region`: that also refuses the isolated partitions' Regions by name, which would newly break `aws-sso` and `aws-iam` integrations that use them for credentials; the console still refuses them, and the cross-partition keys use the full partition check, since isolated partitions have no cross-partition access.

## 2026-11-15: Cross-partition tokens last a minute, are signed with ES384, and never leave memory

A cross-partition role's credentials come from a web identity token that the Identity Center role requests with `GetWebIdentityToken` and that `AssumeRoleWithWebIdentity` exchanges at once. The token asks for `DurationSeconds = 60`, the minimum STS allows: the exchange follows within the same call, so a minute is plenty; a short token fits any `sts:DurationSeconds` limit an administrator puts in the permission set; it can never outlive the source credentials (which `SessionDurationEscalation` would refuse), since those are new for each request and last the permission set's session duration; and a token that leaked would be useless sooner. The default of five minutes buys nothing here. `ES384` is the default signing algorithm because AWS recommends it ("optimal security and performance") and uses it in every cross-partition example, and STS in the destination partition accepts it; `RS256` stays available for an administrator who requires it with `sts:SigningAlgorithm`. The token is a bearer credential for its lifetime, so it is held in a type whose `Debug` output is redacted, sent once, and dropped; it is never cached, logged or written. Only `iss`, `sub` and `aud` are read from its payload, without a signature check, to show in errors and the debug log, because they are what the destination's administrator must match and `sub` (the reserved Identity Center role's ARN) is hard to guess. The AWS SDK logs whole requests and responses at trace level, so the CLI now drops the SDK orchestrator's trace events whatever `OMNIFOB_LOG` asks for, which keeps the token, role credentials and Identity Center tokens out of the log alike.

The exchange is sent from an STS client with no credentials provider, so it is unsigned, as AWS's examples do with `--no-sign-request`: no source credentials travel to the destination partition, where they mean nothing. A `SessionDurationEscalation` is retried once with new source credentials and an `ExpiredToken` once with a new token; `IDPCommunicationError` is left to the SDK, which already retries it as a server error with the same token. `fob console --duration` is refused for these profiles until it is tried live: the federation endpoint refuses `SessionDuration` for credentials from role chaining, and whether an exchange whose token role credentials requested counts as chaining is not documented. Refusing it costs little, since without `SessionDuration` the console session lasts as long as the credentials, and `duration` can make those last up to 12 hours; allowing it and being wrong would fail every console sign-in that sends it.

## 2026-11-15: Smaller release binaries, and only static musl builds for Linux

The release profile uses thin LTO, one codegen unit and stripped symbols. On x86_64 Linux this took `fob` from 34.5 MB (20.9 MB once stripped) to 17.2 MB (17.3 MB for the static musl build), and both release builds took about 2.5 minutes on two jobs. Fat LTO and `opt-level = "z"` were not tried: they trade a much longer build or a slower binary for a little more size. `panic` stays `unwind`, so a panic still prints its message and runs destructors.

Releases are built for x86_64 and ARM64 Linux, Apple Silicon and Intel macOS, and x86_64 and ARM64 Windows. Linux gets only static musl builds (`static-pie`), which start on any distribution, including Alpine; that is the single static binary the Rust entry promises. Up to 0.6.1 Linux had glibc builds from GitHub's Ubuntu runners, and a glibc build from Ubuntu 24.04 needs glibc 2.39, which leaves out Debian 12, Ubuntu 22.04 and RHEL 9. Publishing both would not help them: mise's `github:` backend scores an asset's C library against the host's, so on those glibc systems it would still pick the glibc build that cannot start. The musl build is the same size, and a CLI that spends its time waiting on HTTPS calls gains nothing from glibc's allocator. With one Linux asset per architecture, mise and `cargo binstall` (whose `overrides` in `crates/omnifob` send its gnu targets to the musl archive) need no configuration: mise moves to the musl asset on the next upgrade, and only a mise `asset_pattern` or `matching` that names `gnu` has to change.

The only C in the tree is AWS-LC, through `aws-lc-sys` (rustls' crypto provider, used by the AWS SDK and reqwest). Its sources include `<linux/random.h>`, and Ubuntu's `musl-gcc` wrapper searches only musl's own headers, which do not include the kernel's, so the musl builds use `cargo-zigbuild` with Zig, which ships musl and the Linux kernel headers for every architecture. Windows ARM64 is built natively on `windows-11-arm`, where AWS-LC finds `clang-cl`, and Intel macOS is cross-compiled on Apple Silicon. Asset names keep the Rust target triple, which mise and `cargo binstall` match on; `[package.metadata.binstall]` in `crates/omnifob` names the archive layout.

The build matrix lives in a reusable `build.yml`. `release.yml` calls it on a tag and then publishes; run by hand, it only builds. `ci.yml` calls it too, behind the stack gate, so a new target or a profile change fails on the pull request rather than at release time. The plain release build in the `check` job was dropped: the release build covers macOS and Windows with the real flags, and Linux through the musl targets, while `check` still runs the tests natively on Ubuntu.

## 2026-11-15: End-to-end tests keep secrets in a plaintext test store

The command line had no tests of its own beyond a few unit tests, because every command reads and writes the keychain, and the in-memory store the library tests use (`use_memory_store`) lives only as long as one process, while each `fob` command is a new one. `crates/omnifob/tests` now runs the built binary against a scratch `OMNIFOB_CONFIG` and `XDG_STATE_HOME`, with every provider call sent to a local mock through the existing endpoint variables, and `OMNIFOB_KEYRING=test-plaintext-files:<absolute dir>` puts the secrets in files there. Files rather than the real keychain, because a test must never read or overwrite the maintainer's sign-ins (the keychain is shared, whatever the config path), CI runners have no Secret Service, and parallel tests each need their own store; files rather than a long-lived helper process, because they need nothing running and a test can seed a sign-in or check that a cached credential was deleted by looking at one file.

The store writes secrets unencrypted, so it is built to be hard to choose by accident and obvious when chosen: the name says `test` and `plaintext`, there is no default directory (a bare `test-plaintext-files` or a relative path is refused, so it never lands in the working directory), every process that uses it prints a warning to stderr, `fob status` describes it as "unencrypted files in <dir> (tests only)", and on Unix the directory is created `0700` and each file `0600`, written through a temporary file and a rename so a concurrent command never reads half a value. It is not meant for anything but tests and is documented only here and in `store.rs`. With `OMNIFOB_KEYRING` unset, or set to one of the platform stores, nothing changes.

## 2026-11-16: A browser per integration, defined once in `[browsers]`

People keep separate identities in separate browsers or browser profiles (a personal Firefox profile, a work Chrome profile), and an IAM Identity Center portal session lives in the profile its sign-in opened in. omnifob opened every URL in the system's default browser, so one identity's sign-in landed in another's profile. Browsers are now defined once, under `[browsers.<name>]` as a command with `{url}` in an argument, and an integration names one with `browser`; integrations without it keep the default browser.

The assignment sits on the integration because the integration is what signs in: one Identity Center start URL, Google account or Entra ID account, whose session has to stay in one profile. Defining browsers apart lets one identity's integrations (its AWS portal, Google account and Cloudflare sign-in) share a profile without repeating the command. The same browser opens `fob console`, so the console opens next to the portal session. A console URL is a one-time federation link that works in any profile, so per-profile console browsers (matched by profile id patterns) would be possible; they are left out until there is a need, since the AWS console can hold several identities in one browser profile.

granted has one browser for the console and optionally another for SSO sign-in, set globally (`DefaultBrowser`, `CustomSSOBrowserPath`, or Go-template launch commands), and gives each AWS profile its own Chromium profile by name. A command template, as in granted's launch templates, covers every browser and profile flag without omnifob knowing browsers' install paths or profile folders; it is a list of arguments rather than a string to split, so paths with spaces need no quoting. The browser is started in its own process group (detached on Windows) and not waited for, so a browser that starts with the sign-in outlives `fob`, and Ctrl-C at a prompt does not close it.

## 2026-11-16: `fob login` keeps a browser sign-in that still works, and the callback answers with a page

`fob login` always started a new sign-in. With a portal session still open in the browser, IAM Identity Center approved it without asking for anything, but the browser had still opened a tab for nothing. granted opens nothing while its cached session is valid. `fob login` now checks the stored sign-in of the four browser integrations (AWS IAM Identity Center, Google, Azure, Cloudflare OAuth) the way `fob check` does, renewing it if needed, keeps it when the provider accepts it, and still discovers profiles. A sign-in is kept only when it matches the configuration: an Identity Center session whose client was registered with other scopes, or a Cloudflare sign-in missing a scope fob now requests, is replaced, and so is a session that cannot renew itself and ends within 15 minutes. `--force` signs in regardless, and the sign-in fob starts on its own after a command reports `NeedsLogin` always does, since the stored one was just found lacking. IAM user keys, stored tokens and Cloudflare bootstrap tokens are not kept: for them `fob login` is how the key or token is replaced, and it prompts rather than opening a browser.

The loopback listener answered the browser with one line of plain text, which browsers show as an unstyled page that looks broken next to the provider's own pages. The device flow ends on the provider's page ("Request approved" at AWS), but the browser flow ends at the redirect, so the last page is whatever the listener sends; the AWS CLI sends its own HTML page there. omnifob now sends a small self-contained page (no scripts, images or requests) with a green box when the code arrived and a red one when the provider refused, following the browser's light or dark theme. It says the sign-in was approved, not that it is complete, since the code is exchanged for tokens afterwards and the terminal reports the result. It is omnifob's own page, not a copy of AWS's, because the same listener serves the Google, Azure and Cloudflare sign-ins.

## 2026-11-16: Commands run by a coding agent get no printed credentials and no guessing

Coding agents run fob more and more, and three things differ from a person at a terminal: each command starts in a new shell, so `fob env` and `fob use` cannot carry credentials over and agents fall back on printing them; whatever a command prints is kept in the agent's context and transcripts; and nobody answers a prompt, while some harnesses still give commands a terminal. fob now recognises an agent by the variables agents set (`CLAUDECODE`, `CODEX_SANDBOX`, `GEMINI_CLI`, `CURSOR_AGENT`, `COPILOT_AGENT_SESSION_ID`, the last as the Azure CLI uses it), with `OMNIFOB_AGENT` to name one the list misses or to turn detection off. Detection by marker is unreliable, hence the switch, and the markers are documented as best effort.

Under an agent, `fob creds` in JSON, `fob env` and `fob console --print` (the URL signs in as the role) refuse, naming the `fob exec` command to run instead; the refusal does not mention the override, since agents tend to do what an error suggests. `--format credential-process` and `--format fnox` stay, because the AWS SDKs and fnox run them inside the agent's commands and consume the output; they could not be told apart from an agent running them directly anyway. Prompts are off even with a terminal, a profile must be named by its full id (fuzzy matching picked `tok-a/prod/token` over `tok-b/prod-eu/token` without a word), and an optional `[agent] profiles` list of patterns limits which profiles agents get credentials for, which addresses the larger risk of an agent acting as production admin. None of this is a security boundary: the agent runs as the user and can unset a variable or read the keychain. The harness's sandbox and permission rules are the boundary, and exact ids are what make those rules mean something.

Without an agent, the changes are messages and exit codes. An ambiguous query without a terminal lists how many profiles match and up to ten of them. The note about an integration that is not signed in, which appeared on every command, now appears for `fob list`, `fob export aws-config` and when no profile matches. The MFA hint names `fob exec <id> -- true` rather than `fob creds`, which would print the credentials. `fob exec` exits with 125 when fob fails and 126 or 127 when the command cannot be started, as `env` does, so a caller can tell fob's failures from the command's (a breaking change for scripts that checked for 1).

A sign-in started by an agent keeps waiting until it times out (ten minutes for every browser sign-in, and until the code expires for a device flow: ten minutes for Identity Center, fifteen for Entra ID) rather than returning early, since the callback listener ends with the process and a later run would start over; the skill tells agents to give `fob login` a long timeout. The skill ships in `skills/omnifob` in the repository rather than in `.agents/skills`, which is for skills about developing omnifob, so other people can install it.

## 2026-11-18: Identity Center VPC endpoints and network controls

IAM Identity Center now serves sign-in, the OIDC API and the access portal through interface VPC endpoints, and its network controls can refuse requests that do not come through one. With private DNS on, the usual host names resolve to the endpoint and omnifob needs nothing. Without it, the AWS CLI is pointed at the endpoint with `AWS_ENDPOINT_URL_SSO_OIDC` and `AWS_ENDPOINT_URL_SSO`, so omnifob reads those two as well, honours `AWS_IGNORE_CONFIGURED_ENDPOINT_URLS`, and builds the consent URL from the configured OIDC endpoint, as the AWS CLI does. It does not read the global `AWS_ENDPOINT_URL`, which people set to point the command under `fob exec` at a local emulator: read by omnifob, it would send sign-ins there. The `services` sections of `~/.aws/config` are not read either, since omnifob reads no AWS config file; the variables cover the case without one.

A refusal by network controls says nothing about the session: connecting to the allowed network (usually the VPN) fixes it, and signing in again from the wrong network fails the same way. The refusal used to fall into the generic cases, where a refused renewal (`AccessDeniedException`) ended the session, a 401 from the portal renewed the token and then ended the session, and a 403 was retried as a new account assignment. It is now recognised by its reason, `NETWORK_CONTROLS_ACCESS_DENIED`, and treated as a failure for now with a message that names the network controls. The reason is not in the Rust SDK's models yet (`aws-sdk-ssooidc` 1.124.0, `aws-sdk-sso` 1.122.0), and the portal's error shape is not documented, so it is matched in the response body of any Identity Center error rather than in a modelled field. Neither path has been tried against a real instance with network controls on: turning them on for a real organization risks locking it out, so the mocks reproduce the documented error.

## 2026-11-18: An IAM user's roles last at most an hour

Roles of an `aws-iam` integration are assumed with the user's `GetSessionToken` session, so one MFA code covers every role. The 2026-11-08 entry chose this on the ground that it is not role chaining, so the roles could last up to 12 hours. Tried live, STS counts it as role chaining: a 2 hour `AssumeRole` with session credentials is refused with "The requested DurationSeconds exceeds the 1 hour session limit for roles assumed by role chaining". Every `duration` over an hour therefore failed at the first use. `duration` on an `aws-iam` role and `fob exec --ttl` for one are now 15 minutes to 1 hour, refused when the config loads rather than at STS, and `fob import aws` takes `duration_seconds` up to 3600 for such roles. It is a break for a config with a longer `duration`, which never worked.

Assuming roles with the access key itself would allow 12 hours (aws-vault's `--no-session`), at the cost of an MFA code per role and the key signing every `AssumeRole`. It is left until someone needs longer sessions. (Update 2026-11-25: someone did. `no_session = true` on a role does it, allowing `duration` up to 12 hours; see the entry of that date.)

The same live check showed that role credentials keep working after the session they were assumed with has expired (an hour's role from a session with 15 minutes left answered `GetCallerIdentity` after the session returned `ExpiredToken`), so the duration is no longer shortened to what is left of the session; that only gave shorter sessions. The federation endpoint also returns a sign-in token with `SessionDuration` for these credentials, so `console_duration` on an IAM user's role works although STS calls them chained.

## 2026-11-18: `aws-login` for console credentials

`aws login` gives IAM users, the root user and federated roles short-lived credentials from their console session, with no access key on disk. omnifob does the same as `type = "aws-login"`, following the AWS CLI's implementation (`awscli/customizations/login/`, read 2026-11-18): the same public clients, consent parameters, pasted-code format and error codes, so AWS Sign-In treats omnifob as it treats the CLI. The token calls go through `aws-sdk-signin`, with the DPoP proof added to each attempt by `mutate_request`, which runs after the endpoint is resolved, rather than through an auth scheme like `aws-config`'s, since `CreateOAuth2Token` is unauthenticated and the header is all it needs. The key is P-256 from `aws-lc-rs`, already built into every release through rustls, so no new cryptography crate is added.

The session, DPoP key included, is kept in the keychain like other providers' secrets, not in `~/.aws/login/cache` as plain JSON, so the AWS CLI does not see omnifob's sign-ins and omnifob does not read the CLI's. Sharing that cache would have kept a refresh token and its key in a file. The credentials last 15 minutes and are renewed five minutes before they expire, as the CLI does; refusals that mean the sign-in is over end it, anything else keeps it, as for Identity Center.

There is one profile per integration, the signed-in identity. Roles assumed from it would be role chaining (an hour at most), and nothing asks for them yet. (Update 2026-11-25: they were asked for, and `[integrations.<name>.roles.<label>]` adds them, capped at an hour; see the entry of that date.)

## 2026-11-21: AWS consoles opened apart, one per profile

A federation sign-in replaces the console session in the browser, so `fob console` for a second AWS profile signed out the first. granted avoids it by opening each profile in its own Chromium profile or Firefox container; omnifob now does the same when a browser sets `isolate`. `chromium-profile` adds `--profile-directory=fob <id segments>`, created by Chrome on first use and reused after, so a profile's console keeps its window and tabs; it lives in the normal user data folder, which works for Windows Chrome from WSL, unlike a `--user-data-dir` omnifob would have to place on the Windows side. granted finds a profile by its display name in `Local State` and rewrites that file to rename it; omnifob names the folder instead and leaves Chrome's files alone. `firefox-container` uses the Granted Containers extension's `ext+granted-containers:` URL, so people coming from granted keep the extension they have. The container is named after the fob profile id; colour and icon are left to the extension, which derives the colour from the name.

Only AWS consoles are isolated: their URL is a one-time federation link that signs in by itself in any profile. Google, Azure, Cloudflare and token consoles rely on the browser's existing sign-in, which a new profile or container would not have. AWS console multi-session (up to five identities in one browser profile) was not used: it is opt-in per browser, and a federation link opened from outside the console does not add a session (granted issue #820).

## 2026-11-25: One file writer and one file-name encoding for omnifob's state

`profiles.json`, `history.json`, the Cloudflare catalog and the WSL vault each wrote a fixed `<name>.tmp` and renamed it, so two `fob` processes writing the same file raced on one temporary file, and the vault file was written with the default permissions before being narrowed to `0600`. They now share `omnifob_core::files`, the writer `fob export aws-config` already used for the AWS config: a temporary file named by process id and a per-process counter, created with `create_new` and `0600` on Unix, synced and renamed into place. User files (the omnifob and AWS configs) keep their permissions and symbolic links through `write_atomically`; omnifob's own state goes through `write_private`, which always leaves the file `0600` and creates its directory `0700`, narrowing the state directory, `locks` and `vault` if they were created wider by earlier versions (the vault's file names give away integration names and profile ids). The concurrent read-modify-write of the Cloudflare catalog is a separate fix.

Lock files mapped every character outside `[A-Za-z0-9._-]` to `_`, so profiles `a/b_c/d` and `a/b/c_d` shared one lock and one background renewal. Locks, the vault and the plaintext test store now name files with one percent-encoding (`encode_key_filename`), which also encodes a leading `.` so no name is `.`, `..` or hidden. Vault and test-store names are unchanged for every key omnifob writes; lock files of profile ids get new names, which matters only while an older `fob` runs alongside a new one. WSL detection and the reading of JWT claims (shown, or trusted because they came from the issuer over TLS) are likewise one function each, `platform::is_wsl` and `oauth::decode_jwt_payload`.

## 2026-11-25: Renewals that change a stored sign-in run under a lock, and only final refusals end one

`cloudflare-oauth` renewed its rotating refresh token without a lock, and any failure (a DNS blip, a 5xx) asked for a new browser sign-in; two processes could also spend the same refresh token. It now follows `aws-sso` and `aws-login`: renewal takes a lock per integration, reads the sign-in again once it holds it (a process that waited uses what the first one stored), and only `invalid_grant`, `invalid_client` and `unauthorized_client` end the sign-in, deleting it only if it still holds the refused refresh token. Anything else keeps it for the next try. Azure and Google take the same kind of lock, and `fob login` takes it to store a new sign-in: Entra ID keeps the previous refresh token valid after rotating it and Google does not rotate at all, so for them the lock is not about spending a token twice but about a renewal writing back the sign-in it read over one stored meanwhile. Azure also forgets a sign-in its home tenant refuses with `invalid_grant`, as the AWS providers do. An API call whose access token is rejected before its time (Cloudflare: 401, or 403 with error 10000; Google: 401 from listing projects or impersonating) renews it and tries once more; Cloudflare's other 403s mean a missing permission and are not retried. A `NeedsLogin` raised inside such a call now reaches the caller as itself rather than as a plain error, so `fob` still offers the sign-in.

`aws-login` handed background renewal the credentials it was replacing: `fob renew` asked for new ones, `aws_login` returned the stored session while it had more than five minutes left, and the cache stamped them as issued now, so the lifetime looked shorter at every pass and each `fob exec` spawned another `fob renew`. `fob console` could get credentials with five minutes left. Callers that bypass the cache (`fob renew`, `--no-cache`, `fob console`) now make `aws_login` renew, under its lock, skipping the renewal when the session changed while waiting (another process just renewed it); the credentials carry the time AWS Sign-In issued them, which the cache keeps for `aws-login` only (an `aws-iam` session would otherwise trigger the same loop, since its stored session is reused until it ends). `--ttl` is refused for `aws-login`, as for the other providers whose provider sets the lifetime.

`fob login` keeps a working `aws-login` sign-in too, but only for the Region it signed in through, since its refresh token renews only there. It keeps a Google sign-in only for the configured OAuth client and an Azure one only for the configured tenant (the configured `tenant` is now stored with the sign-in; one stored before matches while `tenant` is unset or names the home tenant). Every browser sign-in now waits up to ten minutes for the callback, as the skill and the agent entry above already said; Google, Azure and Cloudflare waited five. The loopback listener, PKCE and `state` setup shared by the five browser sign-ins is one helper, `oauth::Loopback` and `oauth::Pkce`.

## 2026-11-25: The Cloudflare catalog is updated under a lock, with permission groups per account

Parallel `fob exec` runs on profiles of one Cloudflare integration each loaded the catalog, minted, and wrote it back, so one could drop the token IDs the other had just tracked, leaving minted tokens that cleanup and `fob revoke` never find. Updates now go through a lock per integration that is held only while the file is read, merged and written, never across an API call (a mint takes seconds, and waiting for D1 more). Code that works on a loaded copy (mint, revocation, cleanup) records what it changed, and that change is applied to the file as it is once the lock is held: IDs tracked and untracked, permission groups fetched, the user tag. The lock is synchronous, since `fob login`, `fob logout` and `fob rename` update the catalog from synchronous code, and holding it for a file read and write cannot stall anything. Unlike the renewal locks, which go ahead unguarded after their timeout, the catalog lock fails closed: after a minute of waiting the update is an error, and so is a catalog file that exists but cannot be read or parsed, rather than being taken for an empty one. Either fallback would write back a catalog without the IDs other processes tracked, which a test on Windows showed (8 threads updating at once lost 4 of 80 IDs once). Reads and writes of the file are tried a few times, 50 ms apart, since on Windows a file being replaced or scanned can refuse access for a moment.

The permission groups were one list per integration, fetched from whichever account minted first, so a `cloudflare-oauth` sign-in with several accounts left out optional permissions offered only in another account, or failed to find a required one there until the next refresh. Account-owned tokens now keep a list per account and user-owned tokens one list; the old fields are ignored, so an existing catalog keeps its token IDs and fetches groups again. `fob rename` also renames the profile IDs the token IDs are filed under, under both integrations' locks, and the rename back that `fob rename` does when it cannot write the config restores them exactly; it now reports a failure instead of ignoring it, and warns when `[agent] profiles` still has patterns for the old name.

## 2026-11-25: Secrets stay out of `Debug` output, URLs, logs and shell code

`Credentials` no longer derives `Debug`: its `Debug` lists the variable names with `<redacted>` values, plus the expiry, issue time and token ID, so an embedder's `{:?}`, a tracing field or a failed assertion shows what a profile sets without the secrets. The structs that hold stored sign-ins and tokens (`SsoToken`, `Registration`, the `Stored` of `azure`, `gcp`, `cloudflare-oauth` and `token`, and a minted Cloudflare token's `CreatedToken`) have no `Debug` at all, as `aws_login::Session` and `aws_iam::AccessKey` already had none: nothing needs to print them, and a missing impl cannot leak. Secrets are not zeroized on drop: they are cloned and serialised through `serde_json` and `keyring-core`, which leave copies `zeroize` cannot reach, so it would promise more than it delivers.

Google's `tokeninfo` gets the access token in a POST form body instead of the query string, which proxies and access logs record, as `getSigninToken` already does for AWS. The hard filter on `OMNIFOB_LOG` now drops every trace event of the HTTP and signing crates (`aws_smithy_*`, `aws_sigv4`, `aws_runtime`, `hyper`, `hyper_util`, `h2`, `reqwest`), not only the AWS SDK orchestrator's dumps. Today the one other dump is SigV4's log of the request it signs, but filtering whole crates keeps a dump added by an update out of the log too; their debug events carry no headers or bodies and are kept.

`fob use` and `fob unuse` print shell code for `eval`, and the names of the previous profile's variables come from `OMNIFOB_VARS` in the environment. A name that is not `[A-Za-z_][A-Za-z0-9_]*` is skipped there, since written into `unset {name}` it would run as a command, and credentials with such a name are refused rather than exported. Azure's `nextLink` is followed only on Resource Manager's own scheme, host and port (`OMNIFOB_AZURE_ENDPOINT` in tests), so an answer cannot send the bearer token elsewhere. The DPoP proof's `htu` leaves out the query and fragment, as RFC 9449 requires. `[agent] profiles` patterns are matched segment by segment with a two-pointer wildcard matcher, at most pattern length times segment length steps, where the recursive matcher was exponential in the number of `*`s.

## 2026-11-25: Fewer processes and threads at start-up, and integrations worked on together

On WSL every cached `fob exec` started `powershell.exe -?` (tens to hundreds of milliseconds) only to learn that cached credentials are never written to the DPAPI vault. The vault functions now check the key, and then whether the file exists, before asking whether Windows is reachable, and that question is answered from WSL's `binfmt_misc` interop entry and `powershell.exe` on `PATH`, without starting it. On Linux the Secret Service is skipped without connecting when `DBUS_SESSION_BUS_ADDRESS` is unset and `$XDG_RUNTIME_DIR/bus` (where zbus looks) does not exist; with `OMNIFOB_KEYRING` set, the store it names is used as before.

The CLI runs on a single-threaded Tokio runtime: everything it does concurrently waits on the network, and a worker thread per core only cost start-up time. Building the runtime only for async commands would mean splitting `run`, for less than the threads cost. Each operation builds one HTTP client and uses it for all of its pages (Azure, Google) or tokens (Cloudflare sign-out). A process-wide client is not used: its connection pool would be shared across Tokio runtimes (each `#[tokio::test]`, or a library user's), and a pool from a runtime that has shut down fails with "dispatch task is gone". Superseded on 2026-11-25, below: the client now lives in the library's `Context`, which is meant for one runtime, and the fallback context still builds a client per request.

`fob check` checks every integration at once and prints the results in config order. `fob list` and the commands that pick a profile discover never-synced integrations at once. `fob sync` discovers every integration at once, then signs in again one at a time those that need it (each may open a browser or ask in the terminal), saves every integration that synced even when another failed, and reports the failures at the end. Azure discovery obtains each tenant's token in tenant order, one exchange at a time (each rotates the refresh token, and `arm_token` holds the integration's lock), while the subscription lists of tenants that already have a token are fetched meanwhile; results merge in tenant order, so a subscription seen in two tenants keeps the first, as `az` does. A guest tenant whose subscription list fails is now skipped with a warning, as one that refuses a token already was.

## 2026-11-25: `fob exec` hands the command no stale variables

`fob use` removed the previous profile's variables through `OMNIFOB_VARS`, but `fob exec` passed its whole environment on, so after `fob use` on an R2 profile a `fob exec` on an AWS profile sent S3 calls to R2 (`AWS_ENDPOINT_URL_S3`), and after an AWS profile an R2 profile's key went out with the old `AWS_SESSION_TOKEN`. Both exec paths now remove what `OMNIFOB_VARS` lists and the profile does not set, and `OMNIFOB_VARS` itself, since the command is not a shell `fob use` switched. When the profile hands out an AWS access key, the AWS credential variables it does not set (`AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_CREDENTIAL_EXPIRATION`, `AWS_ACCOUNT_ID`) and `AWS_ENDPOINT_URL_S3` are removed whatever set them, because a key mixed with another key's session token or endpoint never works. Since `fob exec --server`, the other sources of AWS credentials (`AWS_PROFILE`, `AWS_DEFAULT_PROFILE`, `AWS_ROLE_ARN`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_CONTAINER_*`) are removed too, from one list the container endpoint shares. Region variables are the exception: for a profile without a Region of its own, `AWS_REGION` in the shell is usually the user's choice, so it stays; when the profile sets one of the two, the other is removed, so R2's `AWS_REGION=auto` does not sit next to an older `AWS_DEFAULT_REGION`. The command also gets `OMNIFOB_EXPIRES_AT`, as `fob use` now exports it.

## 2026-11-25: Mutating commands are not refused under agents; `fob list` marks what agents may not use

The skill tells agents not to run `fob logout`, `fob revoke`, `fob rename`, `fob login --force`, the `--write` imports and exports or `fob cf add-template` unprompted. fob does not refuse them under an agent: a user who asks the agent to rename an integration or revoke a token would be blocked, and the only way past would be turning agent detection off, which the messages deliberately never suggest. These commands print no credentials, which is what the agent guard is for; the skill and the harness's permission rules govern what the agent decides to do. What fob does change is `fob list`: under an agent with `[agent] profiles` set, it still lists every profile, so the agent can tell the user which one to open, but marks the others `(not open to agents)` (`"open_to_agents": false` in JSON), so the agent does not waste a command on one fob will refuse. Hiding them would make "is not open to agents" errors look like missing profiles.

## 2026-11-25: Shell start-up does not depend on the config, and renewals lock through the OS

`fob activate`, `fob env --unset` and the guidance of a bare `fob use` or `fob unuse` run before the config and `profiles.json` are read, so a typo in the config no longer breaks every new shell, and `fob unuse` still cleans up. A corrupt `profiles.json` is treated as empty, with a warning, by the commands that rewrite it (`fob sync`, `fob login`), only report on it (`fob status`, `fob logout`) or clear what they can without it (`fob revoke --all`, which reads the Cloudflare tokens from the catalog); the rest fail as before, since they would act on profiles they cannot see. `--config <path>` sets `OMNIFOB_CONFIG` for the process before anything runs, rather than being passed down, so every reader of the config and the `fob renew` that fob starts in the background use the same file. A path given with `--config` has to exist (except for `fob import aws --write`, which may create it): a mistyped path would otherwise read as an empty config. `$OMNIFOB_CONFIG` keeps treating a missing file as an empty config, as the default path does.

The background renewal's lock was a file created with `create_new` and considered abandoned after two minutes, so a renewal killed mid-way blocked the next for two minutes. It is now `store::lock` with a zero timeout, an OS lock that ends with the process. Chained roles with `mfa_serial` are not renewed in the background at all: they need a code each session, which a detached process cannot ask for. IAM users' roles still are, since they renew from the stored user session without a code while it lasts.

## 2026-11-25: The config is checked whole when it loads, and has a JSON Schema

Every integration type now checks its keys when the config loads, with the key named in the error: chained roles' account, role, session name and one-hour cap, `https://` start URLs and non-empty scopes, IAM users' role ARNs in the user's partition and Regions in the role's, Cloudflare's `client_id`, `account_id` for account-owned tokens, template names, IP ranges and lifetimes, and token presets, secret lists, variable names and URLs. A mistake used to surface only when a command reached it, sometimes as a token that is never fresh (a Cloudflare `ttl` of five minutes or less) or a profile id two roles share. `fob import aws` runs the same checks, so it skips a profile the config would refuse, with the reason, instead of writing a config that does not load. A token's `verify_url` must be `https://` (or loopback, for tests), since the token is sent there.

Without a home directory omnifob refuses to start unless the variables name its files. Falling back to the current directory wrote `.local/state/omnifob` into whatever repository the command ran in.

The JSON Schema in `schema/config.schema.json` is generated with schemars from the types the config is read into, as a dev-dependency: the derives exist only in the crate's test build, so the library and the binaries do not carry schemars, and a test fails when the committed schema differs from the generated one (`OMNIFOB_WRITE_SCHEMA=1` rewrites it). A hand-written schema would drift silently, and a test could only compare key names, not types or required keys. It is draft-07, which taplo validates, and has no `null` types, which TOML cannot express. The checks that need more than types (partitions, clashing ids) stay in omnifob.

## 2026-11-25: Accounts named alike take their IDs, and profile ids are never shared

Profile ids hold the slug of an account's name, and credentials are cached by id, so two accounts whose names slug alike shared cached credentials. One helper now gives every profile of such accounts `<slug>-<account id>`, for AWS accounts, Azure subscriptions and Cloudflare accounts alike. It is keyed by the slug and the distinct accounts behind it, so all roles of one account move together: the earlier AWS check counted colliding ids, and split one account's roles between `prod-111/Admin` and `prod/ReadOnly`. Any two profiles that still share an id fail the sync.

`fob export aws-config` flattens ids into AWS profile names, so `a-b/c/d` and `a/b-c/d` would share one. The first keeps it and the other is left out with a warning, rather than suffixed: a suffix that depends on the order of profiles could point a name at another account after a sync.

## 2026-11-25: The library works in a `Context`, and its modules follow the providers

`omnifob-core` read its state directory, config path, keychain choice and endpoint overrides from environment variables, kept the keychain and the MFA prompt in process-wide `OnceLock`s, printed a warning to stderr and leaked a string to name the store. A program embedding it could not configure it without setting variables, and every integration test suite took a global mutex to `set_var` its mock server's URL. Everything the library works with is now in an `omnifob_core::Context`: the config file, the state directory, the keychain (`store::Keychain`: the platform's, one by name, in memory, or any `keyring-core` store), whether WSL seals secrets with DPAPI, the MFA prompt, the endpoint overrides (`Endpoints`) and the HTTP client. `Context::from_env()` reads the same variables as before; `Context::builder()` reads none. The keychain is still chosen when a secret is first needed, since choosing one may probe D-Bus. The plaintext test store's warning is a `tracing` warning, which the command line shows by default, and the library denies `clippy::print_stdout` and `clippy::print_stderr`.

Functions find the context as `tracing` finds its span, not through a parameter: the one entered on this thread (`Context::enter`, or `Context::scope` for a future, which enters it on every poll, on whichever thread polls it), else the one the program installed (`Context::install`, which the command line does first thing), else one from the environment. Passing `&Context` through every provider function would have changed several hundred signatures and call sites in one step for the same result; a thread-local re-entered per poll is also safe on a work-stealing runtime, where a plain thread-local guard is not. The cost is that a new thread starts outside the context, so code that spawns one enters it there (as one test does). Each core test now builds its own context with an in-memory keychain, a scratch state directory and its mock's endpoints, so the suites no longer serialize, except Cloudflare's OAuth tests, whose callback port is fixed.

The HTTP client lives in the context, so requests share TLS setup and pooled connections. Clones of a context share the client, and a context is meant for one runtime: the command line installs one for its only runtime. The fallback context, which any runtime may reach, builds a client per request instead, because a pooled connection belongs to the runtime that opened it and fails with "dispatch task is gone" on another.

The largest modules are split by provider: `providers/aws/` (`sso`, `iam`, `login`, `sts`, `console`, `cross_partition`, `partition`), so `aws-iam` and `aws-login` share STS and console sign-in without going through Identity Center's module; `providers/cloudflare/` (`client`, `policies`, `catalog`, `oauth`); and `config/`, one module per integration type plus `browser`, `agent` and `edit`, with the config types still re-exported from `config`. Cross-partition roles got a module of their own, which the plan did not list: their token exchange and error messages are a third of what Identity Center's module held.

## 2026-11-25: `fob exec` serves credentials to SDKs that read no token from the environment

Azure's SDKs and Google's client libraries take no access token from a variable, and AWS credentials in variables cannot be renewed while a command runs. `fob exec` now runs a small HTTP server on `127.0.0.1` for the command's lifetime, in fob's own process (which therefore waits for the command instead of replacing itself with it), each with a random secret that the SDK sends back and fob compares in constant time: an App Service managed identity endpoint for Azure profiles, a token endpoint behind an `external_account_authorized_user` ADC file for Google profiles, and with `--server` an ECS-style container credentials endpoint for AWS profiles. Azure and Google get theirs by default, because without it their SDKs fall back on the user's own `az` or gcloud sign-in, which is not the profile; `--no-server` turns them off. AWS's is opt-in, because the variables already work and the endpoint replaces them. Loopback only, since the AWS SDKs refuse other HTTP endpoints and anything else would expose tokens on the network; one request per connection and a read timeout keep the server small. Connections are answered concurrently (up to 32), so one request waiting for new credentials does not outlast the SDKs' timeouts for the others (botocore waits about 2 seconds per attempt), and the credentials an endpoint handed out are reused while they last 15 minutes or are less than a minute old, which matters under an agent's `max_ttl`, whose requests skip the cache. A failing `accept` (out of file descriptors) is retried after 100 ms rather than at once. The endpoints never prompt for an MFA code: the command shares the terminal, so a request that needs one is answered with an error. Their tasks also carry the library `Context` that was current when they were made, so an embedder can poll them anywhere. Requests and responses are never logged. The files (the ADC file and gcloud's `--token-file`) are private, in the state directory's `run` directory, and deleted when the command ends; a token file left by a killed fob is deleted after two hours. A running command's token file is rewritten at least hourly, even while its token lasts longer (a service account's can last 12 hours), so a second `fob exec` never takes it for a left-over one.

There is no standalone `fob server`: what it would add over `fob exec --server -- <command>` is serving containers, and a container on another network cannot reach the host's loopback while the SDKs refuse a non-loopback HTTP endpoint.

## 2026-11-25: Google executable-sourced credentials carry the account's ID token

The plan was for `fob creds --format gcp-executable` to hand Google's libraries an access token, but the executable contract accepts only an OIDC or SAML subject token, which the library exchanges at Google's STS through a workload identity pool. So the format answers with the account's Google ID token, and `fob export gcp-adc --audience <provider>` writes an `external_account` file for a pool whose OIDC provider trusts `https://accounts.google.com`; the file holds no token. That needs a pool, so the general way to give the libraries a profile's token is the ADC endpoint `fob exec` runs. The ID token is kept from the last renewal, in the keychain with the sign-in.

## 2026-11-25: A `command` integration for other credential tools

`type = "command"` runs a program and reads credentials from its stdout, as the research on awsume proposed instead of in-process plugins: one integration covers saml2aws, gimme-aws-creds, okta-aws-cli, IAM Roles Anywhere's `credential_process` helper and in-house scripts. Two output formats are read: omnifob's own JSON (what `fob creds` prints, so any omnifob profile can be wrapped) and the AWS `credential_process` format, which most AWS helpers already print and which makes the profile an AWS one (stale AWS variables removed, `fob export aws-config`, `fob exec --server`, a federation console link). `format` is set in the config rather than guessed from the output, because whether a profile is an AWS one is decided at discovery, before the program has run.

- The program runs without a shell, from an argument list, so nothing in the config is expanded or needs quoting; it must be a name on `PATH`, an absolute path or one under `~/`, since a relative path would depend on wherever `fob` runs.
- It keeps the terminal's stdin and stderr, since these tools prompt for passwords and MFA and report there; only stdout is read, and its contents never appear in an error, which names the line and kind of problem instead, because stdout holds the secrets.
- It is stopped after `timeout` (default 2 minutes, enough for a browser sign-in; 1 second to 10 minutes) and killed when fob stops waiting.
- Credentials are cached by their stated expiry like any others; credentials without one are not cached at all, since omnifob cannot tell when they stop working and a long-lived key from a helper is cheap to fetch again.
- The lifetime is the program's unless the config sets `ttl`, which says the program takes one: it is passed as `{ttl_seconds}` in the arguments and `OMNIFOB_TTL_SECONDS` in the environment, and then `--ttl` and `[agent] max_ttl` apply through `chosen_lifetime`. Without `ttl`, `--ttl` is refused rather than passed to a program that may ignore it, and `max_ttl` cannot cap it, as for other providers that set their own lifetime.
- `fob login` has nothing to store, and `fob check` runs the program once.

## 2026-11-25: An encrypted file vault for machines without a lasting keychain

On a headless Linux server or a container there is no Secret Service, and keyutils forgets everything on reboot, which the 2026-10-06 entry accepted for then, naming an encrypted-file store as the fix if it annoyed; every reboot means signing in to everything again. `OMNIFOB_KEYRING=encrypted-file` keeps the secrets in files instead, one per keychain key, each sealed with AES-256-GCM under a key derived from a passphrase; the key name is the associated data, so a file renamed to another key does not open. Everything comes from `aws-lc-rs`, already in every build. It offers no memory-hard password hash (scrypt, Argon2), so the key is derived with PBKDF2-HMAC-SHA256 at 600,000 iterations, OWASP's recommendation for it, with a random 16 byte salt. The count is stored in the vault's header, with a known value sealed with the key, which tells a wrong passphrase from a damaged file. A new vault needs a passphrase of at least 12 characters.

The passphrase comes from the library's `Context`, as MFA codes do: `OMNIFOB_VAULT_PASSPHRASE` for scripts and services, else the context's passphrase prompt, which the command line answers in the terminal (asking twice for a new vault). The library never reads a terminal. The derived key, not the passphrase, is then kept in the kernel keyring until reboot, so the passphrase is asked once per boot; `OMNIFOB_VAULT_KEY_CACHE=0` turns that off. Reading a key that has no file needs no passphrase, so commands that find nothing stored do not prompt. Under a coding agent nothing can answer the prompt, so the vault opens only once the user has unlocked it this boot, or with the variable set; the locked-vault error then names only the terminal, not the variable, since the passphrase is the person's to enter. The variable is removed from the environment of `fob exec` commands and `command` helpers, which never need it. A missing `vault.json` beside sealed files is an error rather than the start of a new vault: a new salt would make every existing file unopenable, even with the same passphrase.

What it protects against:

- A copy of the disk, a backup or a stolen machine that is off: the files open only with the passphrase, and the derived key in the kernel keyring is gone after a reboot.
- Other users on the machine: the directory is `0700` and the files `0600`, as for every state file, and the kernel keyring is per user.
- A file swapped for another key's, or changed: it fails to open instead of handing out the wrong credentials.

What it does not protect against:

- Code running as the same user while the vault is unlocked: it can read the derived key from the kernel keyring, as it can read keyutils' secrets today, or ask fob for credentials. That is the same exposure as the Secret Service once the desktop session is unlocked.
- A weak passphrase: PBKDF2 slows guessing, but memory-hard functions would slow it more on GPUs; the iteration count can be raised for new vaults later.
- `OMNIFOB_VAULT_PASSPHRASE` puts the passphrase in the process's environment, readable by the same user and by root; it is for automation that has a secret store of its own.
- The file names, which name integrations and profiles, as the DPAPI files on WSL do.

There is no passphrase change or recovery yet: a forgotten passphrase means deleting the directory and signing in again. The vault is opt-in, and the native keychains stay the default wherever one exists.

## 2026-11-27: Typed browsers, with console isolation on by default

A `[browsers]` entry was a raw command, and keeping AWS consoles apart was opt-in through `isolate`, so a second profile's console signed out the first unless the user knew to set it, and they also had to spell out the browser's install path (from WSL, the Windows one) and its profile switch. omnifob aims to work like mise for cloud sign-ins: typed entries with defaults that work, and a command for everything else. A browser now has a `type` naming one of the browsers fob knows (Google Chrome, Microsoft Edge, Brave, Vivaldi, Chromium, Helium, Thorium, Opera, Arc, Firefox, Zen, LibreWolf, Waterfox, Floorp, Safari, Orion), as an integration has one, and `type = "command"` takes the old command. fob finds a known browser where its installers put it (Program Files and `%LOCALAPPDATA%` on Windows and from WSL, `/Applications` and `~/Applications` on macOS, program names and Flatpak app ids on `PATH` on Linux) unless `path` says, and turns `profile` into `--profile-directory` or `-P`. Asking a browser for a kind it does not have fails when the config loads, rather than opening a broken URL. `isolate = "none"` turns it off. A `command` browser says its `engine` (`chromium`, `gecko` or `webkit`) to get that engine's isolation, so forks fob does not list are covered. Guessing the browser from the command's file name was considered and dropped: it misses wrappers (Flatpak, Snap, scripts) and renamed programs, and it still leaves the path and switches to the user.

The values were renamed after what the browsers call them: `chromium-profile` became `profile` (Chrome, Edge and Brave all call them profiles) and `firefox-container` became `container` (Firefox's Container Tabs, in every Gecko browser, through the Granted Containers add-on). On macOS, Firefox-based and WebKit browsers and Arc open through `open -a <bundle> -u <url>`, as granted does for Firefox, rather than by running the program in the bundle; a Firefox profile is still passed to the program itself, which only `-P` can name. This is a breaking change while the version is 0.x: every `[browsers]` entry needs a `type`, and `isolate` takes the new names. A Firefox profile per fob profile, which would isolate without the add-on, is not done: Firefox runs one process per profile, so each console would be a separate browser instance.

## 2026-11-27: Agents get extra output, people keep their defaults

A review of fob from an agent's side (Claude Code using it as its skill says) found six frictions: a skill copy two releases old, device-code sign-ins whose code an agent cannot relay while the command waits, errors recognisable only by their wording, profiles whose environment and access level an agent had to guess from names, `fob status` calling lapsed sessions "signed in", and options without help. The rule for fixing them: commands behave the same for everyone; agents get additional machine-readable output and a few extra flags; nothing a person relies on changes or goes away. Several of the fixes help people as much.

This entry covers the first and the last two. Every argument now has help text, and a unit test walks the command tree so a new one cannot go without. The skill's front matter names the fob release it describes (`metadata.fob-version`, the Agent Skills spec's free-form map), a test keeps it equal to the crate's version, and release step 1 bumps it. People install the skill with `npx skills add garysassano/omnifob`, which copies it, so fob looks for copies where the agents read global skills (`~/.agents/skills`, `$CLAUDE_CONFIG_DIR` or `~/.claude`, `$CODEX_HOME` or `~/.codex`, OpenCode's config folder), each copy once however many folders link to it. `fob status` notes a copy from another release, and so does `fob list` under an agent, the first command the skill has agents run; nothing is updated without the person. A `fob skill install` command was considered and dropped: it would duplicate `npx skills`, which already installs into every harness.

`fob status` called an Identity Center integration "signed in; renews on next use while the portal session lasts" after the access token expired, though the portal session (8 hours by default) had ended days before; an agent took it at its word. Only the provider knows, so the text now says when the token expired and that it renews "if the portal session is still open", with a closing line naming `fob status --check`, which asks each provider as `fob check` does, shows what it found, and exits 1 when a sign-in fails. In `--json`, `needs_check` marks those integrations and `check` carries the result. `signed_in` keeps its meaning (a sign-in that may work), since status bars read it and an hourly flip to "signed out" for Cloudflare OAuth or console sign-ins, which do renew, would be wrong the other way.

## 2026-11-27: Failures carry a code for agents and scripts

Agents recognised fob's failures by their wording (the skill quoted messages like "name the profile by its full id"), which any rewording broke without a sign. Under an agent, or with `OMNIFOB_ERROR_FORMAT=json`, a failure now ends with one stderr line, `fob-error: ` and JSON with a `code`, the `message` and the values the code needs: the `candidates` of an ambiguous query, the `run` command of a needed login or MFA code, the `profile` kept from agents. People see the message alone, as before; the line is extra output, never a change to it. Exit statuses stay as they are (125 for `fob exec`, 1 elsewhere), since `env`'s convention leaves no room for more, and the codes are what distinguishes.

The library carries the codes: `omnifob_core::Code`, and `Coded`, an error with a code, values and an optional source, which reads exactly as the message it replaces, so the person's output is unchanged. `classify` finds the first `Coded` in an error's chain, maps `Error::NeedsLogin` to `login_required`, and looks through `Error::Other`, whose transparent chain skips the error it holds. The vault hands a coded failure to the keyring crate as itself rather than through anyhow's box, which hides it from downcasting. Only failures an agent acts on differently got a code; everything else is `other` with its message, and new codes may be added without changing old ones. A global `--error-format` flag was considered; the variable reaches nested `fob` runs (credential_process, helpers) and needs no change to every command line.

## 2026-11-27: Profiles carry an environment and an access level

The skill tells agents to pick the least-privileged profile and to ask before production or admin ones, but nothing said which those were: the agent read `prd` and `AdministratorAccess` out of ids, and a person scanning 116 profiles did the same. `fob list` now shows both, and `--json` gives `env`, `access` and where each came from. `[[labels]]` states them by profile pattern (the same patterns as `[agent] profiles`); for each label the first matching entry that sets it wins, so a broad entry can follow specific ones. Without one, a Cloudflare profile's access comes from its template's required permissions (write when any writes or edits, read when all read), and otherwise fob guesses from whole words of the id: environments when exactly one is named (two, as in `dev-to-prod`, give none), and access from AWS's managed job roles, Azure's and Google's basic roles and the usual words, taking the highest when several appear (`ReadWrite` is write), since overstating access is the safer mistake. Every label says its source (`config`, `permissions`, `name`), and text output marks guesses with `?`: an agent must not take a guess for a fact. This is classification, not naming; the 2026-11-25 entry declined tags and aliases as a second naming scheme, and ids stay the only way to name a profile.

The text list gained columns (environment, access, and notes such as `(signed out)` or `(not open to agents)`) at a terminal and under an agent, and prints bare ids when piped, so `fob list | fzf` and scripts keep working. Each profile also says whether its integration's sign-in can give credentials (`sign_in` in JSON, read once per integration), so an agent does not spend a command on a lapsed one. Container colours could select by `env` later; they keep their own patterns for now.

## 2026-11-27: Device sign-ins in two steps

Claude Code, Codex and OpenCode show an agent a command's output only when it ends. `fob login` on a device flow prints the URL and code and then polls for up to fifteen minutes, so an agent could not relay the code while it mattered, unless it happened to run the command in the background and read its output file. The 2026-11-16 entry kept sign-ins in one process because a browser sign-in's loopback listener ends with it; a device flow has no listener. The authorization lives at the provider for the code's lifetime, and anything holding the device code can poll for it.

`fob login --start` therefore starts a device sign-in (Identity Center or Azure), opens the approval page unless `--no-browser`, prints the URL, the code and when it expires, and returns; `fob login --wait` polls with what `--start` kept, stores the sign-in and discovers profiles as `fob login` does. The device code is as sensitive as a token while it waits, since whoever polls with it gets the tokens once the person approves, so it is kept in the keychain (`<type>/<name>/pending`, renamed with the integration) and deleted when polling ends, approved or not, on logout, and when the configured portal or tenant no longer matches. Both steps keep a sign-in that still works, as `fob login` does, so an agent that runs them in turn gets a clear answer either way. `fob login` without the flags is unchanged for people. Browser sign-ins (Google, console sign-in, Cloudflare OAuth) refuse the flags with a message naming plain `fob login`: their window opens on the person's screen, and the agent only has to wait. Google's paste-the-code flow and AWS console sign-in's cross-device flow need a terminal and stay as they are.

## 2026-11-27: Chained roles by rule

Organizations often give every account the same IAM role, such as an administrator role that the account's own power-user permission set may assume. Identity Center does not list such roles, so each one needed a `chained` table naming the account, the permission set and the full ARN: one table per account, and none for accounts created later.

`[integrations.<name>.chained_rules.<label>]` names the permission set, the role name and an optional path once, and discovery applies it to every account where Identity Center lists that permission set. That pairing is already in the listing discovery makes, so a rule costs no calls and cannot be stale. A rule does not check that the role exists in each account: doing so needs `iam:GetRole` with each account's credentials at every sync, and a missing role surfaces as `AccessDenied` or `NoSuchEntity` the first time the profile is used, which says what is wrong. `accounts` and `exclude_accounts` narrow it where the role is known to be absent.

Profiles of a rule are named like the account's Identity Center roles (`<integration>/<account segment>/<role_name>`), not after the rule's label, so they sit next to the permission set they come from in `fob list`, and keep the segment's `-<account id>` suffix when account names slug alike. The profile keeps `Target::AwsChained`, with the rule's label and the account ID it was synced for; config lookups go through `AwsSsoConfig::chained_role`, which returns the `chained` table or the rule applied to that account, so credentials, lifetimes, consoles and MFA behave as they do for a table. A label may therefore not be in both tables. An explicit `chained` table assuming the same ARN wins over the rule in its account, so existing tables can be removed one at a time.

## 2026-11-27: Showing where a stronger role is

An agent denied under one profile had no way to learn that the account has a stronger role it may use: chained roles carried no access label (`acme-root` and its power-user source both showed none), nothing tied a chained profile to the role it is assumed from, and the skill only said to pick the least-privileged profile.

`root` now guesses admin, but only when no other access word is in the name: alone it is an account's break-glass role (`acme-root`), while next to another word it usually names the organization's root account (`root-prd-readonly` is read-only there), where the other word decides. `fob list` and `--json` give a chained or cross-partition profile's `via`, the Identity Center profile it starts from, found by the table's or rule's account and permission set. `fob list --account` takes an account ID or a profile and lists that account's profiles from least to most access, so the role above the one denied is next in the list; profiles without an access label come last, since they may be anything. It filters on the account a profile records, so a chained profile synced before profiles recorded their account appears after the next sync. The skill sends an agent denied an action there, and keeps the rule to ask before an admin or production profile the user did not name.

## 2026-11-27: `fob import aws` writes rules

Configurations that reach an administrator role in every account from that account's power-user role have one profile per account in `~/.aws/config`, and importing them gave one `chained` table each. `fob import aws` now folds roles assumed in the source permission set's own account into a rule when two or more agree on the permission set, the role name and path, and every other key. The rule keeps `accounts`, the accounts the file names, so importing changes no profile; the user drops `accounts` to cover every account, which the file cannot show is safe. Roles assumed in another account than their source stay tables, since a rule always assumes the role in the source's own account.

Importing into a configured portal never rewrites what is there. Roles a configured rule already gives are left out. An imported rule matching a configured rule would otherwise be dropped with the accounts the configured one leaves out, so it is turned back into tables for those accounts instead.
