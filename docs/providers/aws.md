# AWS IAM Identity Center

## Flow

`fob login` signs in the way `aws sso login` does since AWS CLI 2.22.0.

Unlike `aws sso login`, and like granted, it first checks the stored session as `fob check` does (renewing it if needed, then `ListAccounts`), and keeps it without opening the browser when the portal accepts it, it is for the configured start URL and Region, and its client was registered with the configured scopes. `--force` signs in regardless, and so does the sign-in fob starts on its own when a command finds the session refused.

1. `RegisterClient` (name `omnifob`, type `public`, scopes `sso:account:access`). For the browser flow also grant types `authorization_code` and `refresh_token`, the redirect `http://127.0.0.1/oauth/callback` without a port, and the start URL as `issuerUrl`. Registrations are kept per flow at `aws-sso/<integration>/client/<flow>`, apart from the session, and reused until a day before they expire; `fob logout` keeps them, as the AWS CLI does.
2. Browser flow (the default): listen on a free port on `127.0.0.1`, open the consent page (`RegisterClient`'s `authorizationEndpoint`, else the OIDC endpoint the SDK resolves for the region, plus `/authorize`) with `response_type=code`, `client_id`, `redirect_uri`, `state`, `code_challenge_method=S256`, `scopes` and `code_challenge`, wait up to ten minutes for `/oauth/callback`, check `state`, then `CreateToken` with the `authorization_code` grant, the code, the PKCE verifier and the same redirect URI.
3. Device flow (`--device-code`, and on its own when `SSH_CONNECTION`, `SSH_CLIENT`, `SSH_TTY` or `CODESPACES` is set or `/.dockerenv` or `/run/.containerenv` exists): `StartDeviceAuthorization`, show `verificationUriComplete` and the user code, poll `CreateToken`; `AuthorizationPending` keeps polling, `SlowDown` adds five seconds.
4. Store `{start_url, region, access_token, expires_at, refresh_token, client_id, client_secret, client_expires_at}` in the keychain at `aws-sso/<integration>/token`.
5. Before use: refresh with the refresh token when within 15 minutes of expiry, under a file lock per integration (`locks/aws-sso-<integration>.lock` in the state directory), reading the token again once the lock is held. When the refresh fails, the token is used while it is still valid. Once it has expired, or the portal refused it, only the errors `CreateToken` documents as final (`InvalidGrantException`, `ExpiredTokenException`, `InvalidClientException`, `UnauthorizedClientException`, `AccessDeniedException`) delete the session and ask for a new sign-in. Anything else (a network error, a timeout, `SlowDownException`, `InternalServerException`, or another request error such as `InvalidRequestException`) fails the call with "could not renew the sign-in with IAM Identity Center", the cause and a hint to run `fob login` if it persists, and keeps the session for the next try, as the AWS CLI keeps its token cache. `InvalidClientException` and `UnauthorizedClientException` also delete the stored registration of the refused client, so the next sign-in registers again.
6. Discovery: `ListAccounts` then `ListAccountRoles` per account, four at a time, in pages of 100, the most either returns. Profile ids `<integration>/<slug(account name)>/<role>`; colliding slugs get `-<account id>`.
7. Credentials: `GetRoleCredentials` → `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_CREDENTIAL_EXPIRATION`, `AWS_ACCOUNT_ID` (the profile's account, for the SDKs' account-based endpoints), and `AWS_REGION`/`AWS_DEFAULT_REGION` when `default_region` is set.
8. Console: new role credentials (never the cached ones, which are handed out until five minutes before they expire, and the console session ends with them), sent to the federation endpoint of the credentials' partition in the body of a form POST to `getSigninToken` (`Action`, `Session`, and `SessionDuration` in seconds when a console session length is set), so they stay out of URLs, proxy and access logs, and error messages; then a `login` URL to the console, in `--region` or else the Region exported for the profile when there is one. The destination is `https://<console host>/<service>/home?region=<region>` as granted builds it, with `console` as the service when only a Region is given and the bare console host when neither is; `--service` is the path after the host, taken as given (letters, digits, `-`, `_`, `.` and `/`), without granted's shortcut table. Neither the credentials nor the sign-in token are logged; a refused request reports the HTTP status only. Every Region (from `--region`, `default_region`, a role's `region`, the portal's or the STS Region) must be shaped like one (lowercase words joined by hyphens, ending in a number) before it becomes part of a host name, so a value such as `attacker.example#` cannot send the credentials to another host. The partition comes from the role ARN for chained roles and IAM users' roles, and from the portal's Region (or the IAM user's STS Region) otherwise; a Region from another partition is refused, and so are the isolated partitions (`aws-iso`, `aws-iso-b`, `aws-iso-e`, `aws-iso-f`), which have no public console. With an exported Region the sign-in host and the console are regional (`<region>.signin.aws.amazon.com`, `<region>.signin.amazonaws-us-gov.com`, `<region>.signin.amazonaws.cn`, `<region>.signin.amazonaws-eusc.eu`), except in `us-east-1`, `us-gov-west-1` and `cn-north-1`, which use the unprefixed hosts. Without one, both are unprefixed (`signin.aws.amazon.com`, `signin.amazonaws-us-gov.com`, `signin.amazonaws.cn`). The European Sovereign Cloud has no unprefixed sign-in host (`signin.amazonaws-eusc.eu` does not resolve), so there the sign-in uses the portal's Region, else the partition's first (`eusc-de-east-1.signin.amazonaws-eusc.eu`), and the console opens at `console.amazonaws-eusc.eu`.
9. `fob logout`: the portal's `Logout` ends the session at Identity Center, then the token is deleted. An expired access token is renewed first, since its refresh token stays valid at Identity Center until the portal session ends; if Identity Center refuses the renewal, there is no session left to end. If the renewal fails for another reason, `fob logout` warns that the portal session ends on its own when it expires, and still deletes the token.

`GetRoleCredentials` answers 403 for a while after an account assignment is made; omnifob retries twice (after 1 and 2 seconds) before reporting no access, as granted can.

A 401 from a portal call renews the session once and retries. If the portal refuses the renewed token too, or Identity Center refuses the renewal, the session is deleted (only if it still holds the refused token) and a new sign-in is asked for. A renewal that fails for any other reason keeps the session and reports the error.

The SDK clients are built without `aws-config` (the portal and OIDC calls are unsigned), which keeps dependencies down. `OMNIFOB_AWS_ENDPOINT` sends every AWS call to one URL, the console's `getSigninToken` included (at `<url>/federation`; the returned sign-in URL keeps the real host); the tests in `crates/omnifob-core/tests/aws_sso.rs` point it at a mock.

### VPC endpoints and network controls

IAM Identity Center serves its OIDC (`com.amazonaws.<region>.sso-oauth`) and portal (`com.amazonaws.<region>.sso.portal`) APIs through interface VPC endpoints, and its network controls can require every request to come through one. With private DNS on, the endpoint's default, the usual hosts resolve to it from inside the network and nothing needs configuring. With private DNS off, `AWS_ENDPOINT_URL_SSO_OIDC` and `AWS_ENDPOINT_URL_SSO` point the sign-in, renewal and portal calls at the endpoint's own DNS names, as they do for the AWS CLI, and the consent page is then built from the OIDC endpoint rather than the one the client registration names, as the AWS CLI builds it. `AWS_IGNORE_CONFIGURED_ENDPOINT_URLS=true` turns them off, and `OMNIFOB_AWS_ENDPOINT` wins over both. The global `AWS_ENDPOINT_URL` and the `services` sections of `~/.aws/config` are not read.

Network controls refuse a request with `AccessDeniedException` and the reason `NETWORK_CONTROLS_ACCESS_DENIED`, which the Rust SDK does not model yet, so omnifob looks for it in the response body. Such a refusal is reported as one, with a hint to connect to the allowed network, and treated like an outage: a refused renewal keeps the session, and a refused portal call is neither retried as a new assignment (403) nor taken as a revoked token (401).

## Console session length

Without `SessionDuration`, a console session lasts as long as the credentials it was opened with. `--duration` on `fob console`, or `console_duration` on an `aws-sso` integration (for its Identity Center roles) or on an `aws-iam` role, sends one: 15 minutes to 12 hours, and shorter than the role's maximum session duration ("cannot be greater than or equal to"), which for an Identity Center role is the permission set's session duration. omnifob cannot read that maximum, so there is no default, and a refused sign-in names it as the likely cause. The federation endpoint refuses `SessionDuration` for credentials from role chaining and from `GetFederationToken`, so `--duration` is refused before any call for chained roles and for an IAM user's own session, and the integration's `console_duration` is not sent for its chained roles. It is refused for cross-partition roles too until it has been tried (see below). aws-sso-cli sends `SessionDuration` the same way and leaves it out for chained roles; granted sends none.

## Chained roles

Roles reached from an Identity Center role (`role_arn` with `source_profile` in `~/.aws/config`) are configured under `chained`. omnifob gets the Identity Center role's credentials, then calls STS `AssumeRole` with the configured session name and external ID. AWS limits chained sessions to one hour. `AWS_REGION` is exported only when the role or the integration sets a region; STS is called in the portal's region otherwise. With `mfa_serial`, `AssumeRole` sends the device and a code the user types; the credentials are then cached for the session, and parallel requests for the profile wait for one prompt. `AWS_ACCOUNT_ID` is the account in `role_arn`. `duration` sets the session length, 15 minutes to 1 hour, and `fob exec --ttl` overrides it for that command; such credentials are not cached. `fob console` gets new credentials each time, so a chained role with `mfa_serial` asks for a code each time the console opens.

## Cross-partition roles

Roles in another partition are configured under `cross_partition` (the [guide](../guides/aws-cross-partition.md) has the setup in both accounts). omnifob follows AWS's [runtime phase](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_outbound_cross_partition_setup.html), as its CLI and Boto3 examples do:

1. `GetRoleCredentials` for `via_account_id` and `via_role`, as for a chained role (new each time; the result is what is cached).
2. STS `GetWebIdentityToken`, signed with those credentials, in the source Region (`source_region`, else `default_region`, else the portal's): `Audience.member.1` is `audience` and there is no second one (a token with several audiences cannot be exchanged), `SigningAlgorithm` is `signing_algorithm` (`ES384` unless set), and `DurationSeconds` is 60, the minimum. The call is not served by the global endpoint; the SDK resolves the Regional one (`sts.<region>.amazonaws.com`, `us-east-1` included), which a unit test pins. A `SessionDurationEscalation` is retried once with new Identity Center role credentials.
3. STS `AssumeRoleWithWebIdentity` in `region`, from a client with no credentials provider, so the request carries no `Authorization` header or session token, as AWS's examples use `--no-sign-request`: `RoleArn`, `RoleSessionName` (`session_name`, else `omnifob`), `WebIdentityToken` and `DurationSeconds` (`duration`, default one hour, or `--ttl`; 15 minutes to 12 hours, with any fraction of a second rounded up). The SDK retries an `IDPCommunicationError` (modelled as a server error) with the same token; an `ExpiredToken` is retried once with a new token.
4. The credentials, with `AWS_REGION` and `AWS_DEFAULT_REGION` set to `region`, and `AWS_ACCOUNT_ID` the account in `role_arn`. They are cached under the profile; `--ttl` credentials are not.

The token is a bearer credential for its minute: it is never logged, cached or written anywhere, and its `Debug` output is redacted. Its payload is base64-decoded, without a signature check, for one purpose: to show `iss`, `sub` and `aud` in a refused exchange's error and in the debug log, since they are the values the destination's OIDC provider and trust policy must match. Nothing else is read from it. The AWS SDK logs whole HTTP requests and responses, bodies included, at trace level under `aws_smithy_runtime::client::orchestrator`; the CLI drops those events whatever `OMNIFOB_LOG` asks for, which also keeps role credentials and Identity Center tokens out of the log.

Errors name who has to act: `OutboundWebIdentityFederationDisabled` (the source account's administrator enables outbound federation), `AccessDenied` on the token request (the permission set must allow `sts:GetWebIdentityToken` for this audience, algorithm and 60 seconds), `SessionDurationEscalation` after the retry, `AccessDenied`, `InvalidIdentityToken` or `IDPRejectedClaim` on the exchange (the destination's OIDC provider or trust policy, with the token's `iss`, `sub` and `aud`), `IDPCommunicationError` after the SDK's retries, and a `ValidationError` about `DurationSeconds` (the role's maximum session duration). Error codes are matched with and without the `Exception` suffix, since the API reference and the SDK model spell some of them differently; live, STS sent `OutboundWebIdentityFederationDisabledException`, the SDK model's spelling.

`fob check <profile>` checks the profile with `GetCallerIdentity` in `region`, the only partition the credentials work in. `fob console` signs in at the destination partition's federation endpoint, in `--region` or else `region`, so a GovCloud role opens `us-gov-west-1` at `signin.amazonaws-us-gov.com` and a European Sovereign Cloud role `eusc-de-east-1.signin.amazonaws-eusc.eu`. `--duration` is refused: the federation endpoint takes `SessionDuration` for `AssumeRole*` credentials unless they come from role chaining, and whether STS counts an exchange whose token was requested with role credentials as chaining is not documented. Until it is tried, the console session lasts as long as the credentials (`duration`, up to 12 hours).

Tried live on 2026-11-15 in one commercial account, with the AWS CLI and an Identity Center role session (not through omnifob, whose next step would call STS in another partition): before outbound federation was enabled, the token request failed with `OutboundWebIdentityFederationDisabledException`. Once it was enabled, a one-minute ES384 token for one audience came from `sts.us-east-1.amazonaws.com`, while `sts.amazonaws.com` refused the call with `InvalidAction`. The token's `sub` was the reserved role's full ARN with its `aws-reserved/sso.amazonaws.com/<Identity Center Region>/` path. It carried `identity_store_user_id` but neither `identity_store_arn` nor `mfa_present`; the guide's trust policy examples follow that. Outbound federation was disabled again afterwards; a token request right after disabling still succeeded, and later ones were refused.

Not yet tried live, because no account in a second partition is available: the exchange against a real trust policy, whether such sessions count as role chaining (which would cap `duration` at one hour; the `AssumeRoleWithWebIdentity` reference states no such cap, so up to 12 hours is accepted), and `fob console` in the destination partition. `OMNIFOB_AWS_ENDPOINT` sends both STS calls to the mock, which tells them apart by `Action`.

## The AWS config file

`fob import aws` reads `sso-session` sections, legacy `sso_start_url` profiles and granted's keys from `~/.aws/config`, and writes integrations and chained roles.

- `sso_registration_scopes` in an `sso-session` section (comma-separated, as the AWS CLI writes it) becomes the integration's `scopes`; it is left out when it is the default, `sso:account:access`.
- A role whose `source_profile` is an Identity Center profile becomes a chained role, with `duration_seconds` from 900 to 3600, the most AWS allows for role chaining.
- A role whose `source_profile` holds an IAM user's access key becomes a role of an `aws-iam` integration named after that profile, with its `region`, and `mfa_serial` from the source profile or else from its roles; such roles last up to an hour (`duration_seconds` 900 to 3600), since STS counts a role assumed with the user's session as role chaining. A role naming another MFA device than the others is skipped, since an `aws-iam` integration has one. A source profile without Identity Center keys, a role or another credential source is taken to hold a key, here or in the credentials file. The key's values are never read: `aws_access_key_id`, `aws_secret_access_key`, `aws_session_token` and botocore's older `aws_security_token` are dropped as the file is parsed, and the user runs `fob login <name>` to store the key. A profile that is its own `source_profile` (the AWS CLI's way to assume a role with the profile's own key) works the same. Importing again adds only roles missing from an `aws-iam` integration of that name.
- Profiles that cannot be imported are listed with the reason: a role assumed from another assumed role (omnifob chains one role from an Identity Center role or an IAM user), a role whose source credentials come from `credential_source` or `web_identity_token_file` instead of a `source_profile`, a source with `credential_process`, `credential_source`, `web_identity_token_file` or `login_session` (named as the reason even when the source also has a `role_arn`), a source with incomplete Identity Center settings, and a `duration_seconds` outside the range above.
- Comments follow the AWS SDKs' profile parser (the Rust SDK's `prepare_line`): a line starting with `#` or `;` is a comment, and so is the rest of a value from a `#` or `;` that follows a space or tab, so `region = eu-west-1 # home` reads as `eu-west-1` while `x#y` keeps its `#`; in a section header, anything after the `]`. The AWS CLI v2 (botocore's `RawConfigParser`, tried with 2.39.7) keeps inline comments in the value and then refuses the Region `eu-west-1 # home`; omnifob takes the SDKs' reading, which is what such a line means. A line indented more deeply than the property line above it continues that property, as botocore's `configparser` decides, and is skipped: the sub-settings of `s3 =` are, so a nested `region` does not replace the profile's, while a section whose keys are all indented alike keeps every key.

`fob export aws-config` writes a marked block of profiles that call `fob creds --format credential-process`, so tools that read the AWS config get omnifob's credentials; the output includes `AccountId`, which the process credential format allows and the SDKs use like `AWS_ACCOUNT_ID`.

- `--absolute` writes the path of the running binary (`std::env::current_exe`) instead of `fob`, for tools started without the shell's `PATH`. That is the resolved path, with symbolic links followed (for a mise install, the versioned directory), so run the export again after upgrading. A path of letters, digits, `.`, `_`, `-`, `/` and `:` (and `\` on Windows) is written bare. On Linux and macOS any other path goes in double quotes, as the [process credential provider](https://docs.aws.amazon.com/sdkref/latest/guide/feature-process-credentials.html) page asks for a path with a space, unless it contains a character that stays special inside double quotes for `sh -c` (which the Rust and Go SDKs use) or botocore's shell split: `"`, `$`, `` ` ``, `\`, `%` or a control character; such a path is refused with a hint to use `PATH` instead. The AWS CLI 2.39.7 ran a quoted path with a space. On Windows a path that needs quotes (a space, parentheses, `C:\Program Files (x86)\...`) is refused: the Rust and Go SDKs hand the line to `cmd.exe /C` through an API that escapes inner quotes as `\"`, which `cmd.exe` does not undo, and that has not been tried.
- `--write` writes a temporary file next to the AWS config and renames it over the old one, as `fob rename`, `fob cf add-template` and `fob import aws --write` now do for the omnifob config, so a failed write leaves the old file. The temporary file is created anew (never opened through a link left in its place); the file keeps its permissions (set before the contents on Unix), a new one is created `0600` on Unix as botocore creates the AWS config, and when it is a symbolic link the link's target is replaced, so the link stays. The backup of the previous file, `<config>.omnifob-backup`, gets the config's permissions, so a config holding keys is not copied somewhere more readable.

## Multi-Region Identity Center

An Identity Center instance can be [replicated to additional Regions](https://docs.aws.amazon.com/singlesignon/latest/userguide/multi-region-workforce-access.html). Each enabled Region has its own portal URL, without `/start`: `https://<instance id>.<region>.portal.amazonaws.com`, or the dual-stack `https://<instance id>.portal.<region>.app.aws`; the `awsapps.com` URL and custom aliases exist only in the primary Region. The user's portal session is replicated, but "CLI authorizations are not replicated across enabled Regions", so a client registration and token from one Region do not work in another.

omnifob therefore configures an additional Region as a second `aws-sso` integration with that Region's portal URL as `start_url` and the Region as `region`, signed in on its own with `fob login`. Its registrations and tokens are kept under its own name, so the two never mix. `fob import aws` handles both regional URL shapes: they are lowercased like any start URL, keep no `/start`, and without an `sso-session` name the integration is named `<instance id>-<region>`, so a replica's portal does not collide with the primary's. Whether `RegisterClient` accepts a regional portal URL as `issuerUrl` for the browser sign-in has not been tried live on an instance with a replica; if it does not, `fob login --device-code` does without it. A `replicas` list on one integration, tried when the primary Region cannot be reached, would need the Region in the token and registration keys and waits for someone who needs it.

## IAM users

`type = "aws-iam"` keeps an IAM user's access key in the keychain at `aws-iam/<integration>/key`, the way aws-vault does, and never hands it out.

- `fob login` asks for the access key ID and secret (or reads both from `--token-stdin`), refuses temporary `ASIA` keys, checks the key with `GetCallerIdentity` and stores it.
- Profiles: `<integration>/<account or account ID>/session` for the user's own session, and `<integration>/<label>/<role>` per entry under `roles`. The session's account is the `Account` that `GetCallerIdentity` returns; a role's is the account in its `role_arn`. Both are exported as `AWS_ACCOUNT_ID`.
- The session comes from `GetSessionToken`, with `SerialNumber` and a typed code when `mfa_serial` is set, lasting `session_duration` (15 minutes to 36 hours, default 8 hours). It is kept at `aws-iam/<integration>/session` and reused until five minutes before it ends (a session asked for with `--ttl` is used for that command only and not kept); a new one is started under a lock shared by every omnifob process, so parallel commands ask for one code.
- Roles are assumed with the session, and the session's MFA satisfies trust policies that require it: one code covers every role. STS counts this as role chaining, so their sessions last 15 minutes to 1 hour (`duration`, default 1 hour); a longer one is refused with "exceeds the 1 hour session limit for roles assumed by role chaining" (tried live). Their credentials keep working after the user's session ends, so a role's session is not shortened to what is left of the user's.
- Console: session credentials cannot sign in, so the session profile gets a new federated session from `GetFederationToken` with the access key, limited to the user's own permissions by an allow-all policy (as aws-vault does), lasting `session_duration`; that is also the console session's length, since `SessionDuration` cannot be sent with it. Users whose policies require MFA should open the console through a role. A role's console uses new role credentials. Its `console_duration` sends `SessionDuration`, which the federation endpoint accepts for these credentials although STS counts them as role chaining (tried live: it returns a sign-in token); whether the console session then lasts past the end of the user's `GetSessionToken` session has not been watched.

## Console sign-in (`aws login`)

`type = "aws-login"` signs in the way `aws login` does: the browser picks a console session (an IAM user, the root user, or a role reached through federation), and AWS Sign-In hands out credentials for it. No access key is stored, which makes it the alternative to `aws-iam` for IAM users and root. The identity needs `signin:AuthorizeOAuth2Access` and `signin:CreateOAuth2Token`, which the `SignInLocalDevelopmentAccess` managed policy grants; a refusal for that reason names the policy.

1. A browser on this machine (the default): listen on a free port on `127.0.0.1`, open `<Sign-In endpoint>/v1/authorize` with `response_type=code`, `client_id=arn:aws:signin:::devtools/same-device`, `state`, `code_challenge_method=SHA-256` (not OAuth's `S256`), `scope=openid`, `redirect_uri=http://127.0.0.1:<port>/oauth/callback` and `code_challenge`, as the AWS CLI sends them, and wait up to ten minutes for the callback. On a remote or container session, or with `--device-code`, the client is `arn:aws:signin:::devtools/cross-device`, the redirect is `<endpoint>/v1/sessions/confirmation`, and the user pastes the code the page shows, base64 of `state=…&code=…`, whose `state` must match.
2. The Sign-In endpoint is the one the SDK resolves for `region` (`https://<region>.signin.aws.amazon.com` in the commercial partition), or `AWS_ENDPOINT_URL_SIGNIN`, or `OMNIFOB_AWS_ENDPOINT` in tests.
3. A new P-256 key is made for each sign-in, and every `CreateOAuth2Token` carries a DPoP proof (RFC 9449) signed with it: an ES256 JWT with the public key in its header and `htm`, `htu` (the request URL), `iat` and `jti` in its claims, made for each attempt once the SDK knows the URL. The code is redeemed with the PKCE verifier and the redirect URI. The response holds the credentials, a refresh token and an ID token whose `sub` is the console identity's ARN; its signature is not checked, as the AWS CLI does not, since it comes straight from AWS over TLS.
4. The session is kept at `aws-login/<integration>/session`: the identity, its account, the client, the Region, the refresh token, the DPoP key (PKCS#8, base64) and the credentials. The credentials last 15 minutes; within five minutes of expiry the next use renews them with the `refresh_token` grant and the same key, under a lock shared by every omnifob process, and the new refresh token replaces the old one. The refresh token works only in the Region that signed in, so renewal uses the stored Region even if `region` has changed since.
5. `TOKEN_EXPIRED` (the sign-in lasts up to 12 hours), `USER_CREDENTIALS_CHANGED` (a password change) and `invalid_grant` end the session and ask for a new sign-in. Any other failure keeps it: the credentials are handed out while they last, and an expired one reports the error and suggests `fob login` if it persists.
6. One profile, `<integration>/<account or account ID>/<name>`, where the name is the user name, `root`, or the role name of an assumed role. `AWS_REGION` and `AWS_DEFAULT_REGION` are `default_region`, else `region`. `--ttl` has nothing to shorten: the credentials always last 15 minutes from the last renewal.
7. Console: new credentials go to the federation endpoint like a role's, without `SessionDuration`, which is refused for these credentials before any call since they do not come from `AssumeRole`.
8. `fob logout` deletes the session without revoking the refresh token, as the AWS CLI's `aws logout` only deletes its cache; the sign-in ends on its own within 12 hours.

`fob import aws` does not import `login_session` profiles yet: their tokens live in the AWS CLI's cache, which omnifob does not read, so such a profile is listed as skipped and needs `fob login` on an `aws-login` integration.

Not yet tried live: the sign-in, the renewal, whether a role session from Identity Center can be picked, and the console.
