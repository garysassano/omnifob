# Landscape: how cloud CLIs sign in

Studied on 2026-10-06 by reading the sign-in code of each provider's official CLI where it is open source, and the installed gcloud SDK. Rows marked _docs_ come from documentation or prior knowledge, not from reading source; verify them before building a provider.

Akamai has two unrelated credential systems: the CDN and security products use EdgeGrid (`.edgerc`, request signing), while Akamai Cloud still runs on the Linode API (`api.linode.com`) and `linode-cli`, and authenticates with Linode tokens. omnifob would treat them as two providers.

## What stands out

### Three shapes of credential

1. **Session, exchanged for short-lived credentials.** Sign in once, then exchange the session for credentials per account, role or resource: AWS Identity Center, `aws login`, Google (impersonation), Azure, Oracle, IBM, Vercel, Neon. This is omnifob's `aws-sso` shape.
2. **Mint a scoped, expiring API token.** Something with enough authority (a bootstrap token or a browser sign-in) creates narrow tokens on demand: Cloudflare, Linode, Scaleway, OVHcloud consumer keys, Fly.io, Neon API keys. This is omnifob's `cloudflare` shape, and it generalises.
3. **Static tokens only.** DigitalOcean, Hetzner, Vultr, Upstash: no API to create tokens. Akamai EdgeGrid credentials can be created and rotated by API but are long-lived, so they belong here too in practice. omnifob can only store them safely and switch between them. That is still a real improvement, because **every one of these CLIs stores tokens in plain text**; only Cloudflare, Supabase and gh use the OS keyring.

### Browser sign-in, then mint

Akamai Cloud's linode-cli, Scaleway and Supabase all sign in through the browser and then create an API token with the session. Linode and Supabase make it long-lived; Scaleway lets you choose an expiry. Cloudflare's own `cf` CLI requests `account_api_tokens:create` for the same purpose. This confirms the Cloudflare v0.2 plan (OAuth, then mint) and suggests a generic "browser sign-in, then mint expiring tokens" provider shape for Linode, Scaleway and OVHcloud.

### Proof of possession

`aws login` binds its tokens to a DPoP key; Oracle binds session tokens to a key pair and signs every request. A stolen token is useless without the private key. omnifob should keep such keys in the keychain next to the tokens and, where a provider supports it, prefer bound tokens.

### Agents

The Azure CLI already handles agents: when `COPILOT_AGENT_SESSION_ID` is set it asks Entra ID to embed an agent-session claim (`xms_cli_sid`) in tokens, so access control and auditing can treat agent-driven actions differently from human ones. omnifob could mark credentials it hands to agents too: AWS session tags or source identity when assuming roles, a recognisable Cloudflare token name, shorter lifetimes.

### Offline narrowing

Fly.io's macaroons can be narrowed without calling the API. omnifob could keep one broad Fly token and hand out per-app, read-only or hour-long attenuations instantly.

### Refresh timing

botocore refreshes SSO tokens in two stages: advisory 15 minutes before expiry (refresh if possible, otherwise keep using), mandatory 10 minutes before (block and refresh). omnifob uses a single 15-minute window. Background renewal of minted tokens (proposed for the Cloudflare D1 wait) follows the same idea.

### Handing credentials to tools

Not every tool reads environment variables:

- AWS: environment variables, `credential_process`, or a local container credentials endpoint (`AWS_CONTAINER_CREDENTIALS_FULL_URI`, as aws-vault's server mode does).
- Google: `CLOUDSDK_AUTH_ACCESS_TOKEN_FILE` for gcloud, `GOOGLE_OAUTH_ACCESS_TOKEN` for Terraform, and _executable-sourced_ external account credentials in an ADC file, which is Google's equivalent of `credential_process`.
- Azure: most tools call `az` itself (`AzureCliCredential`, Terraform's `use_cli`); there is no common token variable.
- Oracle: config profile plus token and key files.
- Kubernetes: exec credential plugins returning `ExecCredential` JSON with an expiry.

So omnifob needs **provisioners** beyond environment variables: temporary files cleaned up after `exec`, credential-process style helpers per ecosystem, and possibly a local metadata endpoint. 1Password's shell plugins solve the same problem per tool.

### Precedence works in omnifob's favour

Every CLI studied lets an environment variable override its own active profile (`HCLOUD_TOKEN` over the active context, `CLOUDFLARE_API_TOKEN` over OAuth, `DIGITALOCEAN_ACCESS_TOKEN` over doctl contexts). So `fob use` and `fob exec` win without touching each CLI's configuration.

## Design changes this suggests

1. Name the provider shapes in the core: _session exchange_, _mint_, _static_. Providers implement one; the CLI behaves the same for all.
2. Add a generic `static-token` integration soon: keychain storage, multiple accounts, the right variable names. Cheap, and it covers Hetzner, DigitalOcean, Vultr, Upstash and Akamai immediately.
3. Plan browser sign-in for Cloudflare, Linode and Scaleway together; they share a PKCE-then-mint design.
4. Add an `aws-signin` integration for `aws login` (non-Identity Center accounts), with the DPoP key in the keychain.
5. Add provisioners: files with cleanup, `credential_process`, Google executable-sourced credentials, kubectl exec plugin.
6. Add an `--agent` mode: shorter lifetimes, marked credentials, and a record of what was handed to which agent.
7. Two-stage refresh and background renewal.
